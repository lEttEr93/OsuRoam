# 1.5.4：osu! 定位与导入失败

## 症状

朋友机器（osu!lazer，旧配置被清过）：

```
点「导入」→ 什么都没发生。
日志：导入：没有找到 osu 可执行文件，交给系统关联打开 xxx.osz
```

`settings.json` 里 `OsuClient: ""`、`OsuExecutablePath: ""`，而 `.osz` 在那台机器上
**没有任何默认打开方式**（`HKCU\…\FileExts\.osz\UserChoice` 不存在），
于是 `Process.Start("xxx.osz")` 既不报错也不导入 —— 用户看到的就是「点了没反应」。

## 根因

旧逻辑（`BeatmapDownloadService.resolveOsuExecutable`）只有两条路：

1. 设置里手填的 exe；
2. 按 `OsuClient` 的值挑一组**写死的目录**（stable 三个、lazer 两个）。

`OsuClient` 为空时第 2 条走不到分支里，直接返回 null，然后退化成系统关联。
而 `OsuClient` 为空恰恰是「配置被清过」「从旧版本继承」最常见的样子。

顺带两个坑：

- lazer 用 Velopack 安装时，真正在跑的是 `…\osulazer\current\osu!.exe`，
  旧候选列表里只有 launcher 桩 `…\osulazer\osu!.exe`；
- 谱面目录同样写死成 `%LOCALAPPDATA%\osu!\Songs` 和 `%APPDATA%\osu\files`，
  osu! 装在别的盘（很常见）或 lazer 便携安装时，「排除已安装的谱面」直接失效。

## 改动

### 1. 多路探测（`Services/OsuLocator.cs`）

按可信度依次取候选，任一路命中即可用：

| 优先级 | 来源 | 拿到的信息 |
|---|---|---|
| 100 | 设置里手填的 exe | 路径 |
| 90 | 正在运行的 `osu!` 进程 | `MainModule.FileName` |
| 80 | 注册表协议处理程序 | lazer: `osu.Uri.osu` / `osu.File.osz`；stable: `osustable.Uri.osu` / `osustable.File.osz` |
| 70 | 卸载项（`DisplayIcon` / `InstallLocation`） | 两种客户端都能读到 |
| 60 | 常见目录 | 含 Velopack 的 `current\osu!.exe` |

- **客户端从路径推断**（`osulazer` / `…\current\osu!.exe` ⇒ lazer，其余 ⇒ stable），
  不再依赖设置里那个字符串；
- 设置里挑了 lazer 但只装了 stable 时，**照样用 stable**（客户端选错不该让导入彻底失败），
  日志里写明实际用的是哪个；
- 结果按「客户端 + 手填路径」缓存，导入一次不会反复枚举进程。

本机实测（两种客户端都装着）：

```
osu! 定位（按客户端扫）：stable → C:\Users\…\AppData\Local\osu!\osu!.exe（来源：注册表协议）
osu! 定位（按客户端扫）：lazer  → C:\Users\…\AppData\Local\osulazer\current\osu!.exe（来源：注册表协议）
```

### 2. 找不到就明说，不再静默

`import` 里不再有「交给系统关联」这条退路：定位不到 osu! 直接抛
`download.noosu`（「没找到 osu!，谱面没法导入：到「下载与高级设置」点「重新检测」，或填写 osu!.exe 路径。」），
状态栏会把这句话显示出来，卡片标「失败」。
启动失败（`Win32Exception`）也带上具体路径。

### 3. 客户端默认「自动」

`AppSettings.OsuClient` 默认 `auto`，空字符串 / 旧值一律归一成 `auto`。
新用户和旧配置都不再需要先想清楚自己用的是哪个客户端。

### 4. 设置界面能看见检测结果

「下载与高级设置」里，客户端下拉框多了「自动检测」，下面一行显示

```
检测到 osu!lazer：C:\Users\…\osulazer\current\osu!.exe
```

旁边一个「重新检测」按钮（清空缓存重算）。检测不到时用告警色写
「没找到 osu!，谱面会导入失败：点「重新检测」，或在下面填 osu!.exe 路径。」

### 5. 谱面目录跟着安装位置走

`LocalBeatmapLibrary.ResolveRoots()` 改成走 `OsuLocator.BeatmapRoots`：

- stable：`<osu!.exe 所在目录>\Songs`（装在 D 盘也认）+ 默认路径；
- lazer：`%APPDATA%\osu\files` + 便携安装 `storage.ini` 里 `[Storage] FullPath` 指向的 `files`；
- 全部去重、只留存在的目录。

## 验证

- 单测：客户端推断、命令行解析（带引号/不带引号）、`storage.ini` 解析、
  候选顺序（含 `current\osu!.exe`）、谱面目录（沙箱里造三种布局）。
- 实机：把 `settings.json` 的 `OsuClient` 改成 `""`（复现朋友那台机器的状态），
  启动后日志是「设置=auto，候选 3 个 → lazer」，界面上「检测到 osu!lazer」。
- 回归：`排除已安装的谱面` 仍然按 `InstalledBeatmapIds` 走，`tosu` 流程没动。

## 边界（不归 Roam 管）

- **tosu 自己按进程名找 osu!**（`osu!.exe` / `osulazer.exe`，再按 64 位判断是不是 lazer），
  没有 Windows 版的路径参数。它读不到 lazer 内存（`Couldn't read long at 418`）是 tosu 和
  lazer 版本对不上的问题，Roam 这边只能把日志如实写出来，不能替它修。
- `.osz` 的默认打开方式仍然是系统层面的事；1.5.4 之后导入不再依赖它，
  但手动双击 `.osz` 还是需要用户自己关联一次。

# 附：tosu 读不到 osu! 时的提示（1.5.4）

信息栏设成「游戏内选中的谱面」时，数据全靠 tosu。tosu 一旦读不到内存，
界面上原本**什么都没有** —— 用户分不清是没选歌、没开游戏，还是 tosu 挂了。

现在分成三层说清楚：

1. **顶栏**：tosu 日志里出现 `Couldn't read …` 就把「tosu 已就绪」换成
   「tosu 已就绪（读不到 osu!）」，状态栏同时提示一次。
2. **信息窗**：显示一张只有三行的提示卡 —— 标题「tosu 没读到 osu!」、
   原因（琥珀色）、怎么办（灰色）。不画星级/胶囊/键型，因为没有数据。
3. **原因分三种**：

| 情况 | 文案 |
|---|---|
| 读内存失败 | tosu 读不到 osu! 的内存（多半是 lazer 版本比 tosu 新），拿不到游戏内的谱面 |
| 连上了但报不出谱面 | tosu 连上了，但没报出当前谱面：游戏可能没开，或者它读不到这个客户端 |
| 有 ID 取不到文件 | 拿到了谱面 ID，但 tosu 取不到对应的 `.osu` 文件 |

触发时机：选歌界面（`selectPlay`）里报不出谱面 ID、已知读内存失败时回菜单、
`.osu` 取回失败，以及用户主动点迷你播放器的「i」。
同一原因只弹一次，拿到真谱面后重置。

**没有做**「退回显示导入的那张」：用户明确说不需要 —— 导入的谱面可能是另一首，
拿它顶替游戏内的会让信息栏说谎。提示里改成建议用户自己把「信息栏显示」切过去。
