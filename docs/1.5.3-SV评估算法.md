# 1.5.3 SV 评估算法（研究版 v1）

> 记录于 2026-11-07。来源：社区专家研究报告 + 本仓库探针实测 + 玩家逐张试玩反馈。
> 只描述「怎么从 `.osu` 算出 SV 相关的四个量」，不含产品集成方案。

---

## 0. 一句话

osu!mania 的 SV 难度不能用一个分数表达。可行的做法是把它拆成四个可算的量：

| 量 | 回答的问题 |
|---|---|
| **等时性** | 音符等待时间映射稳不稳 |
| **背谱** | 要不要靠记忆（结构差，或 T 远离标称） |
| **不适** | 基线切换发生时，屏幕上待处理的音符多不多 |
| **夸张** | 音符飞行途中的速度变化有多剧烈 |

四个量都只依赖 `.osu` 文本 + 玩家流速设置，不需要回放、不需要人工标注。

## 1. 基础模型：音符可见时长 T

### 1.1 一屏用时

lazer `DrawableManiaRuleset`：

```csharp
public const double MIN_TIME_RANGE = 290;    // 流速 40
public const double MAX_TIME_RANGE = 11485;  // 流速 1
public static double ComputeScrollTime(double scrollSpeed) => MAX_TIME_RANGE / scrollSpeed;
```

```
C = 11485 / 流速
```

流速 25 ⇒ **459.4 ms**；流速 29 ⇒ **396.0 ms**。25 与 29 必须分别积分（分段变速下不能按比例换算）。

### 1.2 归一化速度

```csharp
// MultiplierControlPoint.Multiplier
public double Multiplier => Velocity * EffectPoint.ScrollSpeed * BaseBeatLength / TimingPoint.BeatLength;
```

mania 打开 `RelativeScaleBeatLengths => true`，`BaseBeatLength = Beatmap.GetMostCommonBeatLength()`（按各红线段的累计时长取最常见的拍长），因此：

```
m(t) = SV(t) × BPM(t) / BPM_base
```

- 绝对 BPM 被 `BPM_base` 约掉 ⇒ 220 BPM 与 310 BPM 的谱在同一流速下滚动一样快；
- 谱内 BPM 变化与 SV 变化**完全等价** ⇒ 能识别「用 SV 补偿 BPM」的写法；
- 红线更新 BPM 并重置 SV=1；同一时刻若还有绿线，再取该绿线的 SV。

### 1.3 反解出现时间

```
P(t) = ∫ m(u) du
P(t_i) − P(a_i) = C        ⇒  T_i = t_i − a_i
```

速度按分段常数处理；先累加各段位移，再二分定位区间、段内求解。**不用固定时间步**，避免漏掉极短尖峰。

### 1.4 实现口径

- **和弦头去重**：同一时刻的多个头只算一个时间行，否则多押谱的同一等待时间被重复加权；
- **长条只算头**：T 定义到头部判定，长条尾不参与；
- 拍长限制 6–60000 ms、SV 限制 0.01–10（防御异常文件，非 lazer 官方行为）；
- 开头边界：允许向前外推，但要标记（BLACK MAGIC 首头会算出 11.56 s 这种无意义值，不得混入统计）；
- 长条尾只用于确定谱面结束时间。

## 2. 输出一：等时性（结构）

三层次，全部按 1 秒块统计：

| 量 | 定义 |
|---|---|
| **局部带宽** `localWidth` | 每 1 秒块（≥3 行）的 `(p90−p10)/中位`，汇总取中位与 p90 |
| **基线比** `baselineRatio` | 各秒块中位数的 `p90/p10` |
| **切换事件** | 见下 |

### 2.1 切换事件判定

对每个时间行 t，比较 `[t−1000, t)` 与 `[t, t+1000)`：

| 条件 | 阈值 |
|---|---|
| 两侧样本 | 各 ≥ 4 行 |
| 两侧时间支持 | 各覆盖 ≥ 400 ms |
| 连续性 | 合并区间内相邻行间隔 ≤ 500 ms |
| 基线变化 | `\|ln(中位前/中位后)\| ≥ ln1.18` **且** 差值 ≥ 50 ms |
| **两侧内部稳定性** | 两边 `ln(p90/p10)` 的较大者 ≤ `max(0.22, 0.8 × 基线变化)` |
| 事件抑制 | 与已选事件相距 ≤ 1.5 s 的候选丢弃 |

「两侧都要稳」这一条是关键：**高频抖动不产生切换事件**（两侧 `p90/p10` 大），只有「两个各自稳定的平台之间的跳变」才算。

### 2.2 结构不等时 A

```
A = clamp(0.65 × min(1, 切换次数/分 ÷ 6) + 0.35 × min(1, 局部带宽中位 ÷ 0.5), 0, 1)
```

### 2.3 三种形态的读法

```
局部带宽小 + 基线比≈1 + 无切换  →  全域等时        （Quartzshaper）
局部带宽小 + 基线比大 + 有切换  →  多个等时平台互跳（Star Stream / TWO-TORIAL / Ievan）
局部带宽大 + 基线比≈1            →  持续抖动但同节奏（HOTTO DOGU）
```

## 3. 输出二：背谱

两个互补来源：

```
B_i = max(0, |ln(T_i / C)| − ln(1.10)) / ln2     // ±10% 容忍带内记 0
B   = 0.5 × mean(B_i) + 0.5 × p75(B_i)

背谱 = A² + (1 − A) × B
```

- `A²`：结构已经差时，B 的边际贡献被压到 `1−A`（「再快再慢都不额外增加背谱」）；
- `±10%`：T 在 413–505 ms 之间完全不记偏离；
- 用逐行而非中位数：要抓的正是「个别音符极快/极慢」。

---

## 4. 输出三：不适（舒适度的反面）

对每个切换事件 i：

```
Δ_i = |ln(T_after / T_before)|
n_i = 事件时刻正在飞的待点音符数（a_j ≤ t < t_j 的计数）

sev  = Δ / (Δ + ln2)          // 次线性，3 倍跳变 ≈ 0.6
g(n) = n / (n + 8)            // 1 个 note ≈ 0.11，8 个 ≈ 0.5
p_i  = min(0.6, sev × g(n_i)) // 单事件封顶，避免一次事件决定全曲

不适 = 1 − exp(−Σ p_i)        // 有界、边际递减
```

可选：`p_i` 乘以 `exp(−Δt/20s)`（与上一事件的时间间隔），若认为「隔得久就该重新算」。

**没有独立的等时性事件（`transients`）参与不适计算**——目前只用基线切换。短时偏离是否也要按同样规则扣分，尚未验证。

---

## 5. 输出四：夸张（飞行中的运动）

```
V̄_i = 1 / T_i
夸张_i = (1 / T_i) ∫(a_i → t_i) |ln(V(u) / V̄_i)| du
```

- 匀速飞行 = 0；中途加速、刹车、来回摆 = 正数；
- 无量纲、与绝对流速无关；
- **只统计飞行途中的变化**：SV 在音符之间变化、每颗音符各自匀速飞完时，得分为 0（Star Stream 就是 0.02）。

汇总：全部音符的均值与 p90。

## 8. 已知限制

1. **单人两轮 7 张试玩**，非盲测、非多人统计；
2. **阈值全部手调**，换一批谱可能失效；
3. **`transients`（短时偏离）没进不适计算**；
4. **「屏幕上有几个音符」是模型推定**（`a ≤ t < t_judge` 计数），没有回放数据佐证；
5. **长条只算头**，长条持续期的遮挡/占用未建模；
6. 开头外推值必须标记，不能混入统计；
7. 25 与 29 速各算一套，不能互换。

## 10. 落地（1.5.4）

算法进了程序，算在键型分析里，信息窗显示。

### 10.1 代码位置

| 文件 | 作用 |
|---|---|
| `Services/SvEvaluator.cs` | 全部计算：解析 → 速度曲线 → 飞行时长 → 四个量 |
| `Models/SvMetrics.cs` | 结果模型 + 界面映射（`Isochrony` / `Comfort` / `Intensity`） |
| `Models/ManiaPattern.cs` | 新增 `Sv` 字段，随键型库一起缓存 |
| `Services/ManiaPatternAnalyzer.cs` | `Version` 3 → 4，解析时顺带算一次 SV |
| `Controls/SvRings.cs` | 信息窗里的四个小环 |

计算成本 8–12 ms/谱（740 行时间行），和抓谱面 / 算星数比可以忽略，所以直接挂在分析里，
不另做缓存。

### 10.2 界面映射

信息窗在键型占比条上方放四个小环（顺序固定）：

| 环 | 取值 | 方向 | 配色 |
|---|---|---|---|
| 等时性 | `1 − A` | 越高越好 | 红 → 琥珀 → 青绿 |
| 舒适度 | `1 − 不适` | 越高越好 | 红 → 琥珀 → 青绿 |
| 背谱 | `A² + (1−A)·B` | 越高越差 | 青绿 → 琥珀 → 红 |
| 强度 | `夸张 / (夸张 + 1)` | 越高越差 | 青绿 → 琥珀 → 红 |

- 「强度」用双曲饱和 `x/(x+1)` 压到 0–1：实测夸张 0.02–4.6，这个映射把 0.5–1.5 的常见带摊在中间
  （0.61 → 0.38、1.50 → 0.60、4.58 → 0.82）。
- 环里不写数字，确切值挂在 tooltip 上 —— 卡片宽度只有 390px，四位数放不下。
- 数值为 0 时仍画一小段弧：空环看起来像「没数据」，而 0 是「测出来就是 0」。
- 环只在 mania 谱面出现（键型分析本来就只做 mania）。

### 10.3 与探针的实现差异

1. **不适**：探针用连乘 `1 − Π(1−p)`，落地版按 §4 写成软和 `1 − exp(−Σp)`，
   单事件严重度改成 `Δ/(Δ+ln2)`、承载 `n/(n+8)`、单事件封顶 0.6。
   两种写法在实测谱上差 ≤0.03。
2. **飞行时长**：探针逐段回溯积分，落地版先建分段线性的 `P(t)` 再二分反解，
   结果一致（432 张谱：等时性平均偏差 0.002、夸张 0.001）。
3. **行过滤**：开头距离不够一屏的行（`T ≤ 0.001`）直接丢弃，和探针口径一致。

### 10.6 首次解析与动画节奏

SV 自己只花 8–12 ms，但它是**键型分析的一部分**，整份分析（键型匹配 + 星数 + MinaCalc +
SV）是几十到几百毫秒。所以问题不在 SV 本身，而在「什么时候算」：

1. **信息栏 = 游戏内谱面**：原来是「解析完才出窗口」，选歌时按方向键会明显卡一下。
   现在详情（元数据 / CS·OD·物件数）先算先出，窗口立刻显示；键型与 SV 丢到线程池，
   算完回填到同一个条目，雷达 / 直方图 / 四个环自己长出来。
2. **算过的直接复用**：结果进键型库（`patterns.json` 里连 `SvMetrics` 一起序列化），
   换首歌再转回来命中缓存，不再重算。游戏内浏览过的谱面也会入库。
3. **动画一次只放一遍**：三个控件各有生长动画，而 `Labels` / `Values` 是分开赋值的，
   每个属性都会触发一次 `beginGrowth` —— 肉眼看到的就是「长一遍、缩回起点、再长一遍」。
   改成 `SetData(...)` 批量赋值（批量期间 `onDataChanged` 不放动画，收尾放一次），
   并且键型对象没变（封面加载完的那种刷新）就整块跳过。

实测（临时探针日志，一次显示窗口）：直方图 1 次、四环 1 次、雷达 1 次。
