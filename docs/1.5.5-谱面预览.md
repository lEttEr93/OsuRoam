# 1.5.5：选歌界面的谱面预览

## 要做什么

选歌界面里，osu! 会播一段预览音频。把这段音频的当前位置（毫秒）从 tosu 读出来，
在旁边开一个和信息窗**等高**的窗口，用当前谱面的 `.osu` 实时滚一遍 mania 谱面 ——
「这首歌打起来长什么样」不用进游戏也能看到。

皮肤只做最简单的轨道 + 方砖：白砖是单点，粉色长条是 LN，不做判定、不播声音、不读皮肤文件。

## 数据来源

| 用途 | payload 字段 | 说明 |
|---|---|---|
| 什么时候显示 | `state.name == "selectPlay"` | 和「信息栏显示游戏内选中的谱面」同一个开关条件 |
| 哪张谱面 | `beatmap.id` / `beatmap.version` | 换这两者任一就当换歌 |
| 预览音频位置 | `menu.bm.time.current` | gosumemory 兼容段；tosu 的 `/json/v1` 里一直有 |
| 退路 | `beatmap.time.live` | v2 的同一把尺（`global.playTime`），两个值是同一个数 |
| 谱面文本 | tosu `GET /files/beatmap/file` | 和信息窗共用 `TosuFileClient` 的缓存，不额外下载 `.osz` |

tosu 源码里这两处都是 `global.playTime`：

- `packages/tosu/src/api/utils/buildResult.ts` → `menu.bm.time.current`
- `packages/tosu/src/api/utils/buildResultV2.ts` → `beatmap.time.live`

所以「优先菜单段、没有就用 v2 字段」不会读到两个不同的时间，只是为了兼容不同版本的 payload。

两个都读不到（字段是 0）时窗口不装懂：底部时钟停在 0，2.5 秒后中间浮一行
「tosu 没给预览音频位置，画面停在原地」。

## 时钟：为什么不能直接用快照里的毫秒数

tosu 的 WebSocket 快照不是每帧都来（默认几十毫秒一条，还带网络抖动）。
直接把快照里的时间当帧时间，画面就一格一格跳。`Services/PreviewClock.cs` 干这件事：

| 情形 | 处理 |
|---|---|
| 正常（距上一条 < 200ms） | 每帧按墙上时间前进，再补掉 15% 的差 |
| 差值 > 200ms（换歌、预览被拖回去） | 直接对齐，不做平滑 |
| > 200ms 没有新值（预览暂停 / 断流） | **停在原地**，不回退到旧值（回退等于画面倒退两三百毫秒） |
| 换歌 | `Reset()` 后第一条精确落位，不从上一首滑过去 |

这套数学单独成类就是为了能离线测：`Tests/Program.cs` 里三个用例分别验证
「一秒后跟得上」「停更不再前进」「跳变直接对齐」。

## 渲染

`Services/ManiaPreviewChart.cs` 只抽「第几列、什么时候、多长」：

- 列号 `floor(x * keys / 512)`，`keys = Difficulty.CircleSize`（1–10，超界夹最后一列）；
- 长条取 `HitObjects` 第 6 段的 `endTime`（`24000:0:0:0:0:` 这种）；
- 只认圈（type&1）和长条（type&128），滑条/转盘是转换谱面的残留，丢掉；
- 不是 mania（`Mode != 3`）、没有物件、键数离谱 → `null`，窗口不出现。

`Controls/ManiaPreview.cs` 每帧只画画面里的物件：物件按起点排序，先二分找到
「当前时间 − 最长长条」之后第一个，再往后画到超出画面上沿。两万物件的谱面也是
每帧几十个矩形，不会卡。

| 参数 | 值 | 理由 |
|---|---|---|
| 可见时长 | 1.25s | 10 NPS 时画面里 12 个物件，够看密度又不糊 |
| 判定线离底 | 26px | 下面一条带子画键位，不做判定 |
| 砖高 | `laneWidth × 0.17`，夹 7–20px | 列宽跟着窗口走，砖不会瘦成线 |
| 轨道 | 隔列压深色 + 1px 分隔线 | mania 皮肤里最常见的读谱辅助 |

## 布局

- 高度：跟信息窗 **完全一致**。信息窗可见时读它的 `ActualHeight`；
  信息窗收着时读它记下的卡片高度（量不到退回 420）。
  实测 421.0（信息窗）/ 420.7（预览窗），差的 0.3px 是窗口边框取整。
- 位置：贴在信息窗右侧 8px；右边放不下就翻到它左边，再不行贴屏幕右缘。
  信息窗没开时贴着主窗口右下那条线，和信息窗默认落点一致。
- 跟随：主窗口移动/缩放、信息窗长高（键型补图、换语言）都跟着走 ——
  窗口自己的渲染循环每 200ms 复查一次位置和高度，变了才赋值，不做无谓布局。

## 回落

| 情况 | 表现 |
|---|---|
| 设置里关掉「选歌时显示谱面预览」 | 立刻收起，下次不再弹 |
| 不在选歌界面 / 没有谱面 ID | 收起 |
| 开局 / 结算 / 回菜单 | 收起（和信息窗一起，在游玩时隐藏那一套逻辑里） |
| 拿不到 `.osu`（tosu 给不出文件） | 不弹，日志记一行 |
| 不是 mania | 不弹，日志记一行 |
| 预览音频位置一直是 0 | 弹，但轨道静止 + 中间提示一行 |

## 验证

开发参数（都在 `--snapshot` 下）：

```bash
OsuRoam.exe --preview  --snapshot=preview.png   # 预览窗 + 信息窗等高（顺带截 -info.png 对照）
OsuRoam.exe --preview=noclock --snapshot=noclock.png   # 模拟 tosu 不给位置，验证提示
```

日志会打一行状态：

```
预览窗：h=420.7 w=430.0 top=594.0 left=484.0 chart=4K/2266 time=30982ms source=30982ms notes=13
信息窗高度：421.0（预览窗 420.7）
```

`chart=4K/2266` 是「4 键 / 2266 个物件」，`notes=13` 是这一帧真正画出来的物件数。

## 渲染管线（第二版：独立 D3D11 通路）

第一版用 WPF 自己画，帧率从 100 提到 210fps，但**帧时间不稳**：p50 4.7ms、p95 15.8ms，
约 5% 的帧迟到 3–4 个刷新周期。原因不在绘制（0.04ms），而在：WPF 是保留模式、由 UI 线程
产生帧，主线程上任何活（tosu 快照、封面解码、键型计算、GC）都会把那一帧挤掉。

所以预览单独走一条管线（`Controls/PreviewSurface.cs`）：**子窗口 + 自己的 D3D11 交换链 +
自己的渲染线程**，和 WPF 只通过两个字段交互（换谱面、喂 tosu 的预览位置）。

| 环节 | 做法 |
|---|---|
| 呈现 | `CreateSwapChainForHwnd`（`FLIP_DISCARD`）+ `Present(1, 0)` |
| 节拍 | `FrameLatencyWaitableObject` + `LatestFrameLatency=1`：等到合成器要下一帧才画，不忙等 |
| 绘制 | Direct2D 画矩形（轨道/砖/长条/判定线），一次 `BeginDraw`/`EndDraw` |
| 时钟 | 渲染线程自己按 `Stopwatch` 外推（`PreviewClock`），UI 线程每 100ms 只更新读数和摆位 |
| 资源 | 翻转模型的缓冲区会轮转 → 每个缓冲区一套 D2D 目标 + 画笔（`FrameResources`） |

实测（同一台机器，2560x1600 / 240Hz，物理 645x630）：

| 实现 | p50 | p90 | p95 | p99 | max | >20ms 帧 | 绘制耗时 |
|---|---|---|---|---|---|---|---|
| WPF 分层窗口 | 10.0 ms | — | 21.2 ms | — | — | 19 / 235 | — |
| WPF 普通窗口 + DrawingVisual | 4.7 ms | 8.0 | 15.8 ms | 19.6 ms | 21.3 ms | 3 / 425 | 0.04 ms |
| **D3D11 独立管线（现在）** | **4.2 ms** | **4.2** | **4.3 ms** | **4.4 ms** | **5.4 ms** | **0 / 732** | **0.22 ms** |

p50 4.2ms = 240fps，正好锁在刷新率上；p99 与 p50 只差 0.2ms，也就是**帧时间几乎是常数**。

### 怎么复测量

```bash
run.cmd --preview=fps --snapshot=x.png                      # 帧时间统计
run.cmd --preview --snapshot=x.png --preview-shot=frame.png  # 把渲染线程画的那一帧从显存读回来
run.cmd --preview --snapshot=x.png --preview-hold=8000       # 让预览窗多停一会儿（抓屏用）
```

日志一行：

```
帧率探针（fps）：732 帧｜p50=4.2 p90=4.2 p95=4.3 p99=4.4 max=5.4ms ≈240fps
｜>20ms 0 帧｜绘制 0.22ms｜逻辑 430x420｜物理 645x630@1.5x
```

> 想确认画面本身对不对，别用抓屏：翻转模型的交换链在 `BitBlt`/`PrintWindow` 里通常是黑的
> （可能被提升成硬件覆盖层）。用 `--preview-shot=` 从显存读回来才作数。
>
> 踩过的两个坑：① 翻转交换链每帧缓冲区会轮转，`GetBuffer(0)` 一直取会画到前面那块 →
> 屏幕全黑；② Direct2D 不包在 `BeginDraw`/`EndDraw` 里，绘制命令根本不会提交，
> 表现也是全黑、耗时 0.0xms。

## 已知边界

1. **lazer 的预览时钟**：lazer 下 `beatmap.time.live` 取的是 `FramedBeatmapClock`
   的最终时钟，选歌界面里它未必在走。真遇到就是上面那条「位置一直是 0」的提示。
   stable 下读的是同一把 `playTime`，gosumemory 时代的 `menu.bm.time.current` 就是它。
2. **预览音频自己循环**：osu! 的预览播完会重头再来，时间会跳回去 —— 跳变分支负责对齐，
   肉眼看是一次正常的画面重置。
3. **非 mania 不显示**：转换谱面（std 谱在 mania 里玩）走的是 osu! 运行时的转谱，
   `.osu` 里还是 std 物件，这里不做转换，直接不显示。
4. **预览画面不再是 WPF 元素**：赛道那块是子 HWND，所以它不能被 WPF 内容盖住、
   也不能做圆角裁剪（卡片圆角在它外面，赛道本身是矩形，视觉上没问题）。
   另外分层窗口（`AllowsTransparency`）和子 HWND 不兼容 —— 分层模式已废弃。
