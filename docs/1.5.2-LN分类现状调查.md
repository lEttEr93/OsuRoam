# LN（长条）谱面的技能分类现状调查

> 调查日期：2026-11-03。目的：搞清「LnRatio + RC/LN/Mix/HB 模式标签」这套体系里，**长条谱面到底能得到哪些技能分类**，以及我们和上游差在哪。
> 方法：① 精读本仓库 `Services/ManiaPatternAnalyzer.cs` 全文；② 扫描本机已安装谱面算真实分布；③ 拉上游 `osumania_map_analyser` 源码逐文件比对；④ 用一次性探针在真实分析器源码上跑合成谱。
> 本文只记录现状，不涉及实现改动。

---

## 1. 结论摘要

1. **模式标签本身不产生任何"长条专属分类"**。它只做两件事：
   - `RC` 时丢弃 `Coordination / Density / Wildcard` 三个核心族的匹配（`Analyze()` 第 51–52 行）；
   - 上游还有一层**按模式加权的倍率表**（`SUBTYPE_RATING_MULTIPLIER_BY_MODE`），**我们没有移植**。
   `LN / HB / Mix` 三个标签走**完全相同**的检测管线，代码里没有任何一处按 `HB` 或 `LN` 分支。
2. 真正由长条判据定义的分类，我们只有 **8 个**：`Column Lock`、`Release`、`Shield`、`Inverse`、`JS Density`、`HS Density`、`Speedy WC`、`Jacky WC`。上游还有 **3 个 7K LN 密度**（`DS Density`、`DCS Density`、`LCS Density`）我们没有。
3. 但 LN 谱**不止**出这 8 个名字。`Stream` / `Chordstream` / `Jacks` 三族在 LN 谱上照样能触发（长条头被当成单点计入 `Notes`），只是常常在份额竞争里排第二，所以看不见。
4. 实测本机 3134 张 mania 难度：**RC 68.5% / HB 16.5% / Mix 14.3% / LN 0.7%**（纯长条只有 22 张）。`LN` 标签几乎不出现，长条谱绝大多数落在 `HB` 与 `Mix`。
5. 一整套「上游怪癖」其实是**原样移植**的（`MsPerBeat` 语义、`HbRowRatio` 分母、`RELEASE_FULL_MATCH_ROWS` 不可达、`CORE_STREAM` 首尾同列判据），不是我们写错。
6. 真正的移植缺口是**管线少了一层**：上游是 `find → 聚类 → 剪枝 → 每核心取前 3 → 按 Importance 取第一个 cluster 命名`，我们是 `find → 直接按时间份额聚合 → 命名`。

## 2. 模式标签的实际作用（代码事实）

```
LnRatio <= 0.15        → RC    → 丢弃 Coordination/Density/Wildcard 的匹配
LnRatio >= 0.90        → LN
HbRowRatio >= 0.10     → HB    （仅在 0.15 < LnRatio < 0.90 时参与）
否则                    → Mix
```

- `LnRatio` = 长条头数 /（普通音符 + 长条头），与上游 `lnPercent()` 完全一致。
- `HbRowRatio` = 同一行同时出现长条头与普通音符的行数 / 总行数，与上游 `hbRowRatio()` 一致（**分母都包含只含长条体/尾的行**，所以长条越密 HB 越被低估——上游同样如此）。
- 上游把标签拆在 `modeTagFromLnRatio()`（只出 RC/LN/Mix）与 `summary.js resolveModeTag()`（tag=Mix 且 hb≥0.1 才改判 HB）两处，行为与我们合并写法等价。

**关键点**：`RC` 不是"没有长条"，而是"长条 ≤15%"。所以 RC 谱里仍有长条，第 51 行的过滤是活代码（关掉它会显著改变 `CoreShares`、`SpecificShares` 与 `Tech` 后缀）。

## 3. 我们这边：LN 谱可达的分类

### 3.1 长条判据的 8 个（唯一由 LN 字段驱动的）

| 子型 | 核心型 | 触发条件（源码实证） | 阈值 |
|---|---|---|---|
| `Column Lock` | Coordination | 首行有 LN 头 → 取其列；该列 body 期间，同手相邻列出现普通音 ≥3 次，且相邻间隔换算 BPM ≥90 | 90 BPM、3 hits、8 行窗口 |
| `Release` | Coordination | 前 4 行每行**恰有 1 个尾**、排除 Shield/Inverse/Jacky、前两条有效尾列不同且 Δt>0 | 4 行扫描、2 roll points |
| `Shield` | Coordination | 相邻两行 Δt ≤0.25 拍，且「a 普通音列 = b 长条头列」或「a 尾列 = b 普通音列」 | 0.25 拍 |
| `Inverse` | Density | 连续 5 行**零普通音** + 某行 body ≥3 列 + ≥2 次「尾→头」交替且间隔差 ≤5ms | 3 列、5ms、5 行 |
| `JS Density` | Density | 首行有 LN 头，把头行前 4 行压成"只看头"的伪行后套 4K 跳流判据 | 4 行（4K） |
| `HS Density` | Density | 同上但套 4K 交互判据（3 音头 + 4 行无叠键，4K 上几乎不可达） | 4 行（4K） |
| `Speedy WC` | Wildcard | 有长条上下文 + 头行呈 Roll / 同向 / 行距 ≤45ms(4K) 或 ≤42.5ms(非4K) | 180 / 170 |
| `Jacky WC` | Wildcard | 有长条上下文 + 前 4–6 个有音符行里出现 chordjack / minijack / ≥2 行叠键 | 6 行窗口、185 |

`Coordination` 的判据是「本行 `LnHeads | LnBodies | LnTails` 任一非空」⇒ 长条谱里**几乎每行都触发**；`Density` 与 `Wildcard` 的判据**完全相同**（都只看 `LnHeads>0`），只靠子型拉开差距，相等时按固定枚举顺序决胜（Coordination > Density > Wildcard）。

### 3.2 实际会出现在 `Category` 里的取值

`Category` = 主导核心型名，若其最显著子型占该核心型质量 >5% 则换成子型名，再按需加 `" Tech"`（分组内节奏不稳比例 >50%）。

字面值空间封闭：6 核心名 + 20 子型名 + `Jumpstream/Handstream` + `Uncategorised` = 28 个，每个可加 `Tech`。LN 谱不可能出 `Uncategorised`（Coordination 必然触发）。

合成谱探针实测（约 35 000 张）：LN 谱上真实出现过的基础值 11 个 + 9 个 Tech 变体 —— `Coordination`、`Release`、`Inverse`、`Shield`、`Jacky WC`、`Speedy WC`、`JS Density`、`HS Density`、`Stream`、`Chordstream`、`Longjacks`。其余（`Column Lock`、`Chordjacks`、`Minijacks`、`Quadstream`、`Gluts`、`Jumpstream`、`Handstream`、`Split Trill`、`Jumptrill`、`Rolls`、`Trills`、`Minitrills`、`Jumpstream/Handstream`）只在很窄的构造下可达。

### 3.3 真实数据

本机已安装谱面（stable `Songs` + lazer `files` 联合扫描）：

| 标签 | 张数 | 占比 | LnRatio 中位 |
|---|---|---|---|
| RC | 2147 | 68.5% | ≤0.05（49.8% 的谱面 <5%） |
| HB | 516 | 16.5% | 0.317 |
| Mix | 449 | 14.3% | 0.240 |
| LN | 22 | 0.7% | 0.973 |

4K 单看：RC 1609 / Mix 376 / HB 363 / LN 17。

真实分析缓存（`%LOCALAPPDATA%\OsuRoam\patterns.json`，5 条记录）里两张长条谱：

| 谱面 | LnRatio | HbRowRatio | 标签 | Category | 核心份额 |
|---|---|---|---|---|---|
| 4504765 | 0.216 | 0.019 | Mix | `Release Tech` | Coordination .30 / Stream .26 / Wildcard .25 / Density .16 |

即：**长条谱的实际输出常常是 `Release Tech`**，而 `Release` 在这两张里只占全部匹配时长的 2%。命名由 5% 门槛（相对主导核心型）决定，样本极薄。

## 4. 与上游对照

上游 `LeoBlackMT/osumania_map_analyser`（MIT，Rust 后端 + `ManiaMapAnalyser by Leo_Black/js/patterns/` 前端分析器）。

### 4.1 常量：全部一致

`LN_MODE_LOW/HIGH`、`HB_ROW_RATIO`、`PATTERN_STABILITY`、`CATEGORY_JS_HS_SECONDARY_RATIO`、`JACKY_MIN_BPM`、`SHIELD_MAX_BEAT_RATIO`、`INVERSE_GAP_TOLERANCE_MS`、`INVERSE_MIN_FILLED_LANES`、`RELEASE_SCAN_ROWS/MIN_TAIL_ROWS/ROLL_POINTS/FULL_MATCH_ROWS`、`JACKY_CONTEXT_WINDOW`、`JACKY_FALLBACK_MAX_MSPB`、`MATCHER_WINDOW`、5% 子型门槛 —— 逐一核对无偏差。

### 4.2 子型注册表：我们缺 8 个

| 键数 | 上游 | 我们 |
|---|---|---|
| 4K · Stream | Rolls / Trills / Minitrills | 同 ✓ |
| 4K · Chordstream | Handstream / Split Trill / Jumptrill / Jumpstream | 同 ✓（上游另有 `Double Jumpstream`、`Triple Jumpstream` 两个**也从未注册**的函数） |
| 4K · Jacks | Longjacks / Quadstream / Gluts / Chordjacks / Minijacks | 同 ✓ |
| 4K · Density | Inverse / JS Density / HS Density | 同 ✓ |
| **7K · Chordstream** | `Brackets` / `Double Stream` / `Dense Chordstream` / `Light Chordstream` | **空** ❌ |
| **7K · Density** | `Inverse` / `DS Density` / `DCS Density` / `LCS Density` | **只有 `Inverse`** ❌ |
| 其它键数 · Chordstream | `Chord Rolls` + Double/Dense/Light Chordstream | **空** ❌ |
| 其它键数 · Density | Inverse + DS/DCS/LCS Density | **只有 Inverse** ❌ |
| 非 4K · Stream | 空 | 空 ✓ |

`DS / DCS / LCS Density` = 把「只看长条头」的伪行套 7K 的 Double Stream / Dense Chordstream / Light Chordstream 判据，是 **7K 长条谱的密度三件套**。本机 7K 占 702 张（22%），这些谱的 `Density` 族目前只有 `Inverse` 一个出口。

子型顺序也有差异：上游 `COORDINATION_SPECIFIC_ORDER = [Column Lock, Shield, Release]`，我们注册的是 `[Column Lock, Release, Shield]`。

### 4.3 管线：少了两层

上游：

```
find() → calculateClusteredPatterns()（按 pattern + BPM 聚成 cluster）
      → 剪枝 canBePruned / BPM>25 过滤
      → 每核心型取 Importance 前 3
      → 排序后取第一个 cluster，用它的 SpecificTypes[0] 命名
      → `${name}${hybrid?" Hybrid":""}${tech?" Tech":""}`
```

我们：`findMatches() → 按时间份额直接相加 → 用主导核心型的聚合份额命名`。

后果：
- 上游 `Category` 描述的是**一个连续时间簇**，我们描述的是**全谱时间占比**；
- 上游 5% 门槛的基数是"该 cluster 内子型占比"，我们的基数是"该核心型的聚合质量"；
- 上游有 `Importance` 概念（含 BPM/密度），我们没有；`IMPORTANT_CLUSTER_RATIO`、`CLUSTER_SPECIFIC_NAME_MIN_RATIO` 未移植；
- 上游 `resolvedMspb()` 对 `Density+Inverse` 把 MsPerBeat 归零（影响聚类），我们无聚类所以无对应行为。

另外上游的 `Hybrid` 后缀是**死代码**（`isHybridChart()` 恒返回 `false`），所以我们不出 `Hybrid` 是忠实移植。

### 4.4 权重层：整层缺失

上游 `config.js` 有 `SUBTYPE_RATING_MULTIPLIER_BY_MODE`，按模式给每个子型不同倍率（例：`Inverse` 在 HB/Mix 下 = **0.0**、`Release` 在 HB/Mix 下 = 0.3、`Column Lock` 1.5、`Jacky WC` 0.55/0.65/0.45、`Speedy WC` 0.8/0.45），并有 `RC_CORE_LN_SCALE = 0.3`（LN 模式下把 rice 三核心型压到 0.3）与 `RC_LN_CORE_SCALE = 0.0`。

这层用于**难度评级**，我们本来就不算图案评级，暂时不影响功能；但它意味着我们的 `CoreShares` 与上游不是同一套度量，**跨工具比份额没有意义**。

### 4.5 原样继承的上游怪癖（不是我们写错）

| 现象 | 出处 |
|---|---|
| `MsPerBeat = 行间隔 × 4`（不是 ms/beat），所以 `2000 / 185 / 180 / 170` 实际是行距阈值 | 上游 `primitives.js` 同式 |
| `HbRowRatio` 分母含只含体/尾的行 → HB 被低估 | 上游 `summary.js` 同式 |
| `RELEASE_FULL_MATCH_ROWS = 5` 不可达（只扫 4 行） | 上游同样不可达 |
| `CORE_STREAM` 要求首尾行首列不同 → 周期 2 trill、周期 4 四键楼梯不匹配 | 上游 `CORE_STREAM` 同判据 |
| 同一窗口多子型同时命中会各记一条（`ENABLE_MULTI_LABEL_SAME_WINDOW = true`） | 上游同名开关，**有意为之** |
| `Shield` 同时覆盖「单点→长条头」与「长条尾→单点」两种方向 | 上游同名函数；后者在 osu!wiki 里是**独立的 `Reverse shield`** |

## 5. 术语校正（依据 osu!wiki）

| 术语 | wiki 定义 | 我们代码 |
|---|---|---|
| `Shield` | 同一列中**紧挨在长条头之前**的普通音符（手感接近 minijack） | 覆盖，但名字与判据都偏宽 |
| `Reverse shield` | 长条尾之后**紧跟**同列普通音符 | 被算进 `Shield`，**没有独立分类** |
| `Inverse` | 所有音符换成长条、每根延伸到同列下一根之前，形成"长条墙" | 判据吻合（5 行无单点 + 尾→头等距 ±5ms） |

来源：<https://github.com/ppy/osu-wiki/blob/master/wiki/Beatmap/Pattern/osu%21mania/Hold_note/en.md>

配套的社区常用 LN 说法（有据可查，可作为将来扩分类的词汇表）：LN / long note / 长条 · rice / 米 · release / 尾判 · LN wall（"面条海"）· LN jack · LN overlap · short LN（40–250ms）· chunked release（同时放手）vs independent release（独立放手）· hold coverage。**查不到确证**的说法（不要当对外分类名用）：`LN stream`、`LN trill`、`roll LN`、`long note stamina`。

### 5.1 生态现状：有"分类"，没有"技巧计算"

| 项目 | LN 分类 | LN 难度/技巧计算 | 依据 |
|---|---|---|---|
| MMA（osumania_map_analyser） | ✅ 11 个 LN 子型（纯规则） | ❌ 只有「份额 × 倍率」的图案评级，无标定、无验证 | 本文件第 4 节，源码核实 |
| Interlude（YAVSRG） | ❌ | ❌ 只有 `LNPercent`、`HoldCoverage` 这类度量 | 上游源码 |
| Etterna / MinaCalc | ❌ | ❌ **结构上不可能**：`NoteInfo` 只有行位掩码 + 行时间，`Skillset` 7 项无 LN，pattern mod 全集无 hold 项 | 官方源码 |
| osu! 官方 mania SR | ❌ | ⚠️ **有，但很粗**：`OverallStrainEvaluator` 用 holdFactor 1.25（被别的长条罩住）+ `holdAddition` = 对「本音符尾到最近其他尾的距离」的 logistic（`release_threshold = 30ms`）——注释原话"同时放手和只放一个一样简单"，即**独立放手更难**。但长条时长/密度、锁手、inverse 都不参与；分量只进单星单轴 | [Strain.cs](https://github.com/ppy/osu/blob/master/osu.Game.Rulesets.Mania/Difficulty/Skills/Strain.cs)、[OverallStrainEvaluator.cs](https://github.com/ppy/osu/blob/master/osu.Game.Rulesets.Mania/Difficulty/Evaluators/OverallStrainEvaluator.cs) |

结论：**LN 的"技巧清单"本身还没定稿**（wiki 只到 shield / reverse shield / inverse / release 这种命名层），也没有任何经过标定的量化分级。唯一公开的 LN 难度项是 osu! 官方 mania SR 里那两条（holdFactor + release 分离度 logistic），粗到只值几个百分点，但它的**思路**（放手越孤独越难）与玩家说的"狗啃面"完全一致，可以直接借。其余场景社区给 LN 分难度靠的是人肉段位表（LN Dan courses / Phase I–III）。所以"狗啃度"这类量**没有可比对的成熟标准**，只能自证。

## 6. 缺口与优先级

**A. 7K / 非 4K 的 LN 密度三件套（最高）** —— `DS Density` / `DCS Density` / `LCS Density`，以及 7K 和弦流的 `Brackets` / `Double Stream` / `Dense Chordstream` / `Light Chordstream` / `Chord Rolls`。现成判据在上游 `patternsDef.js`，照抄即可。不做的话，7K 长条谱（本机 22% 的谱面）只能落到 `Inverse` 或裸 `Coordination`。

**B. 让 `Category` 有统计意义** —— 现在的 5% 门槛相对"主导核心型的聚合质量"，一张长条谱可能因为 2% 的 `Release` 被命名为 `Release Tech`。要么补上游的聚类 + Importance，要么把门槛改成相对**全谱时长**。

**C. `Reverse shield` 独立成项** —— wiki 级标准术语，加一个方向判断即可（现有 `Shield` 检测器把两种方向混在一起）。

**D. 单列 hold jack 无出口** —— `coreJacks` 要求 `Jacks > 1`（≥2 列重叠），同列连续长条只有 1 列叠，直接不参与。实测得到裸 `Coordination`。

**E. `Release` 没有"尾判时机"语义** —— 它只比较"尾列是否交替 + Δt>0"，从不比较尾部与节拍网格；社区说的 release timing / awkward release 完全没有度量。

**F. 尾行打断连续判定** —— 长条尾会生成 `Notes=0` 的空行，`Stream / Chordstream / Jacks` 的"连续 N 行有音符"判据一律被切断，这是 LN 谱里 rice 族难以主导的结构性原因。

**G. 七轴看不见长条的形状** —— 本地估算 `buildSkillAxes()` 只认 `Jumpstream / Handstream / Chordjacks / Minijacks / Trills` 等 RC 子型名，8 个 LN 子型对七轴贡献**全为 0**；`Stamina` 用 `TotalNotes` 算 NPS，长条只算 1 个音符，耐力被系统性低估。MinaCalc 路径只喂音头掩码：**长条头被当成单点计入**（所以数量、分布、叠键、和弦其实都算进去了），但长度、键位占用、尾完全丢失 —— Etterna 的 `NoteInfo` 只有掩码 + 行时间，`NoteData::SerializeNoteData2` 注释即 "only send tap data to calc"，尾不生成行。

## 7. 「狗啃面 / 整齐的面」在现有算法里的位置

玩家说的两种面：

- **整齐的面**：长条头/尾都落在同一批拍点上，多根长条同时放、同时收，读谱只需"看块"。
- **狗啃面**：头尾各自错开，或单点嵌在长条之间，读谱必须逐列分辨"这一根什么时候收"。

### 7.1 现有算法里最接近的三样东西

| 现有机制 | 与"狗啃度"的关系 | 局限 |
|---|---|---|
| `Mixed` → `Tech` 后缀 | 判据是「该匹配窗口内各行的行距（`MsPerBeat` = 行距×4）与窗口均值偏差 ≥5」——端点错开会导致行距不匀，所以**它实际上在无意识地度量狗啃度** | 只看行距，不看端点；5 的阈值相对约 300+ 的量级只有 ~1.5%，极其敏感；单行匹配（裸 `Coordination`）永远判不出 `Mixed`；只在主导分组 `mixedRatio > 0.5` 时变成 `Tech` 后缀 |
| `Release` | 要求「前 4 行每行**恰有 1 个尾**」——这正好是"独立放手"（= 狗啃的尾）的结构特征 | 只判有无交错，不判错开多少；且被 `Shield` / `Inverse` / `Jacky` 排斥 |
| `Inverse` | 要求尾→头间隔差 ≤5ms，即**完美等距的整齐长城** | 只覆盖最极端的整齐形态（且要求 5 行零单点、≥3 列同时持有） |

`Speedy WC` / `Jacky WC` 与这个问题**无关**：它们只是把 `hasLnContext` 当作准入门槛，实际判的是速度与叠键。

### 7.2 实测：现有代理确实与「面齐不齐」高度相关

扫本机 22 张纯 LN 谱（`LnRatio ≥ 0.9`），逐张算两个量：

- **端点重合度** = 端点（头或尾）所在行还有别的东西的占比 —— 越高越"整齐"；
- **行距不匀率** = 现有 `Mixed` 判据的全局版本（5 行窗口，阈值 5）。

| 端点重合度 | 行距不匀率 |
|---|---|
| 0.466 | 0.973 |
| 0.792 | 0.920 |
| 0.808 | 0.758 |
| 0.855–0.873 | 0.396–0.683 |
| 0.910（5 张） | 0.181 |
| 0.930 / 0.932 | 0.123 / 0.362 |
| 0.975（4 张） | 0.057 |

**基本单调、只有个别倒挂**：现有 `Mixed`/`Tech` 机制虽然是为"节奏不稳"设计的，但在长条谱上确实跟着"面齐不齐"走 —— 因为两端错开必然打乱行距。

但它是**相对量**，分不清"狗啃的长条"和"本身节奏就碎的 rice 谱"，也没法告诉用户"这张谱的面有多碎"。

### 7.3 缺失的、真正对得上这个概念的量

以下四个都只需要现有 `parseChart` 已经产出的行数据（`LnHeads / LnTails / NormalNotes` + `chart.Bpm`），一次线性扫描即可，不需要新检测器：

| 指标 | 定义 | 语义 | 实测（22 张纯 LN 谱） |
|---|---|---|---|
| `EndpointCoincidence` | 端点中「所在行还有别的头/尾/单点」的占比 | 面齐不齐（主指标） | 0.47 – 0.98，中位 0.91 |
| `TailSimultaneity` | 含尾的行里「同拍 ≥2 个尾」的占比 | 同时放手 vs 独立放手 | 0.09 – 0.53，中位 0.37 |
| `ShortLnShare` | 时长 40–250ms 的长条占比 | 「短面条」风格 | 0.37 – 0.97，中位 0.91 |
| `GridOffsetP90` | 端点离最近 1/4 刻度的距离 P90（拍） | 是否用了 1/6、1/8 等更细的格 | 0.000 – 0.124 |

注意：osu 谱面基本都吸附网格，所以**中位数几乎恒为 0**（实测 0.000–0.003 拍），单看"离网格多远"没有区分度，有意义的是 P90 与"端点是否彼此同拍"。

### 7.4 建议的落点

「狗啃度」是**可读性维度**，与 6 个核心型（手型族）正交。放进子型会破坏现有结构，建议按 `SvAmount` 的做法存成 `ManiaPattern` 上的图表级标量，然后在信息栏显示成一行文字（例：`面齐整度 82% · 独立放手 31% · 短面条 74%`），并让它参与 `Tech` 后缀的判定（替代或加权现有的 `Mixed` 布尔）。这样不需要新增任何核心型/子型，也不影响推荐引擎的向量。
