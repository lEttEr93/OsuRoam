# 1.5.1 开发笔记

## 已修：导入下一首要等新谱面下载完（计划里的「计划修复 1」）

症状：池里 5 张都预下载好了，但触发「导入下一首」时，要等后面新加入的那张下完才动。

根因在两处串行化：

1. `BeatmapDownloadService.DownloadAsync` 一开始就 `await queue.WaitAsync()`，
   **即使文件已经在缓存里**也要排在预下载后面；
2. `ImportAsync` 用的是**同一把** `queue`，所以导入本身也被一次几个 MB 的下载挡住。

改法：

- `DownloadAsync` 先查文件（存在且 ≥1024 字节）→ 直接返回，不进队列；
- `ImportAsync` 换成独立的 `importGate`，只串行化「校验 + `Process.Start`」，
  不再和下载抢；
- `MainWindow.downloadItemAsync` 把「确保下载」和「确保解析」拆开：
  已 `Downloaded` 的不再调下载，只在 `Detail`/`Pattern` 缺失时补解析
  （重启后缓存还在但没解析过的情况也能覆盖）。

## 已做：更好的去重（计划里的「计划新增 1」）

调研结论（tosu v4.26.1，源码 `packages/server/router/v1.ts`）：

- `GET /Songs/{path}` 会遍历 osu! 的 Songs 目录；`GET /Songs/` 返回 **HTML 目录列表**
  （`<li><a href="...">文件夹名</a></li>`），不是 JSON。
- 必须有 osu! 在运行：否则 500 `{"error":"osu is not ready/running"}`。
- osu!stable 的目录名是 `<setId> <artist> - <title>`，所以**一次请求**就能拿到整个
  已安装曲库的 set id；要拿「哪些难度已装」得逐目录再请求一次。

**lazer 实测把上面这套推翻了**：`/Songs/` 返回的是内容寻址仓库（`0/` → `00/` …），
目录名全是十六进制前缀，没有 setId 可用；`/json/v2` 里的 `folders.songs` 是
`...\AppData\Roaming\osuiles`，`files.beatmap` 是 `<sha256>` 相对路径。

所以改成**直接扫本地目录**（`Services/LocalBeatmapLibrary.cs`），不依赖 tosu：

- stable：`%LOCALAPPDATA%\osu!\Songs\<setId> artist - title\*.osu`，按扩展名筛；
- lazer：`%APPDATA%\osuiles\<hex>\<hex>\<sha256>`，读前 24 字节认 `osu file format`，
  确认是谱面再读 8KB 抠 `[Metadata]` 的 `BeatmapID` / `BeatmapSetID`；
- 两个目录**都扫并取并集**（很多人两个客户端都装着）。

实测（这台机器）：stable 242 个文件 + lazer 20340 个文件 → **3943 个难度 / 720 个谱面集**，
冷扫 **2.0 秒**，缓存命中 **73 毫秒**。

两个性能坑：
1. 别用 `FileInfo.Length` 做大小预筛——19k 次串行 stat 要 10 秒以上；读 24 字节判断同样便宜，还能并发；
2. 先读 24 字节再读 8KB，别对每个音频文件都读满 8KB。

去重语义按「难度」来：`RecommendationEngine.Rank` 多了 `excludedBeatmapIds`，
命中已装的 BeatmapID 才跳过，**同一首曲子的其他难度仍然可以推荐**——这是计划里
括号写的那条（「同一首歌的不同难度不进行去重」）。

设置里新增「排除已安装的谱面」（默认开）。tosu / osu! 没开也照样能用，这一步不依赖它们。
