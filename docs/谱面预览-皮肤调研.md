## 0. 结论先行

### 0.1 lazer 流畅来自哪两个设计决定

**决定 1：绘制线程唯一的节拍源是"交换链/合成器的帧就绪"，不是 sleep、不是自旋、也不是游戏自己的定时器。**
```csharp
// osu.Framework/Platform/GameHost.cs:509-521（DrawFrame 开头）
if (didRenderFrame && !isVrr)
    Renderer.WaitUntilNextFrameReady();
didRenderFrame = false;
buffer = drawRoots.GetForRead(IsActive.Value ? TripleBuffer<DrawNode>.DEFAULT_READ_TIMEOUT : 0);
```
`WaitUntilNextFrameReady` 一路下到 Veldrid 后端（`VeldridDevice.cs:253-254` → `Device.WaitForNextFrameReady()`）：**呈现相位由 API 层保证，应用层不猜 vblank**。

更新线程相反，是"超前跑"的：VSync 模式下绘制限速设为无穷、更新限速设为刷新率×2 再翻倍，且封顶 `maximum_sane_fps = GameThread.DEFAULT_ACTIVE_HZ = 1000`：
```csharp
// osu.Framework/Platform/GameHost.cs:1355-1391
case FrameSync.VSync:
    drawLimiter = int.MaxValue;
    updateLimiter *= 2;        // 进入 switch 前 updateLimiter = 刷新率*2 → 这里变成 *4
    break;
...
MaximumDrawHz = drawLimiter;
MaximumUpdateHz = executionMode.Value == ExecutionMode.SingleThread ? drawLimiter : updateLimiter;
// osu.Framework/Threading/GameThread.cs:23
internal const int DEFAULT_ACTIVE_HZ = 1000;
```
⇒ 240Hz 屏：更新约 960Hz 持续产出，绘制被交换链钉在 240Hz。**每次"可以出帧"时绘制线程早已阻塞在等待点、手里已有现成的树**，Present 在刷新周期内尽可能早发出，留给 DWM 的合成窗口最大。"帧时间稳但偶尔多留一个刷新周期"最相关的不是队列深度，而是 **present 在刷新周期里的相位**。

**决定 2：时间被插值并单调钳制，位置每帧平滑，不随音频时钟抖动。**
```csharp
// osu.Framework/Timing/InterpolatingFramedClock.cs:129-159
currentTime += realtimeClock.ElapsedFrameTime * Rate;
currentTime = Interpolation.DampContinuously(currentTime, framedSourceClock.CurrentTime, DriftRecoveryHalfLife, realtimeClock.ElapsedFrameTime);
...
bool elapsedInOpposingDirection = framedSourceClock.ElapsedFrameTime != 0 && Math.Sign(framedSourceClock.ElapsedFrameTime) != Math.Sign(Rate);
if (!elapsedInOpposingDirection)
    currentTime = Rate >= 0 ? Math.Max(lastTime, currentTime) : Math.Min(lastTime, currentTime);
```
结论：**相位靠 API 保证 + 时间不回退**。不是靠调交换链参数。

### 0.2 我们能抄的三件事（按性价比）

| # | 抄什么 | 映射到 D2D/D3D11 | 预期收益 | 验证 |
|---|---|---|---|---|
| 1 | 等待 vsync 是唯一节拍源，且**等待点前移到取帧数据之前**；更新侧 2–4× 刷新率超前，绘制侧 0 sleep | 保留 `FrameLatencyWaitableObject`+`MaximumFrameLatency=1`；删掉绘制循环里的 `DwmFlush`/`Sleep`/自旋；`WaitForSingleObject` 移到"取当前 tile 描述"之前，取完立刻 `Present(1,0)`，中间只留 `BeginDraw/EndDraw` | 若 5% 多留一帧来自相位漂移则直接命中；改动成本极低 | PresentMon：`msUntilDisplayed` 直方图 / `Dropped` 计数 / Present 相对 vblank 的偏移分布 |
| 2 | 一帧一 Present、present 前不做任何 GPU 同步 | 生产路径禁止 `Flush`/`Map`/`Query`/`WaitForGPU`；截图类只在调试开关后 | 减少错过 DWM 截止的概率，Present 时刻更可预测 | `msInPresentAPI` 稳定性；帧时间 P99 |
| 3 | 整帧四边形压进一个动态 VB，一次 `DrawIndexed`（按状态分段，段数越少越好） | (a) 继续 D2D：按画刷排序 + 单一 `ID2D1BitmapBrush`（ExtendMode Wrap）+ 复用 transform；或 (b) 直接 D3D11：`DYNAMIC` VB + 预建索引 + 图集/纹理数组，一帧 1–3 次 draw | 收益在**尾部**（避免偶发状态切换慢路径），不是均值 | RenderDoc/PresentMon：draw call 从"每矩形"降到个位数；`msInPresentAPI` 尾部 |

### 0.3 判断

皮肤只决定"长什么样"，不决定"何时 present"。帧时间问题解决前做皮肤是错的排序。皮肤 P0 走「用户导出 .osk」或「skin.ini + 贴图目录」，**不读 realm**（见 E.6）。

## A. 帧循环

### A.1 线程

| 角色 | 类型 | 位置 |
|---|---|---|
| 线程基类（状态机 + 单帧体） | `GameThread` | `osu.Framework/Threading/GameThread.cs:21` |

| 帧编排 | `GameHost` | `osu.Framework/Platform/GameHost.cs:492-580` |

**update 与 draw 是两个线程**；单线程模式顺序跑所有线程：
```csharp

case ExecutionMode.SingleThread:
    foreach (var t in threads) t.RunSingleFrame();
case ExecutionMode.MultiThreaded:
    mainThread.RunSingleFrame();   // 主/输入线程仍跑在窗口循环里
```

单帧体（`GameThread.cs:425-475`）：`Scheduler.Update()` → `synchronizationContext.RunWork()` → `OnNewFrame()` → `Clock.ProcessFrame()`。**帧时钟在帧末推进**，且被计入 `PerformanceCollectionType.Sleep` 段。

### A.2 帧节奏由谁保证（三层叠加）

1) **`ThrottledFrameClock` 主动 sleep**——整个框架唯一的主动等待：
```csharp
// osu.Framework/Timing/ThrottledFrameClock.cs:62-72
double excessFrameTime = 1000d / MaximumUpdateHz - ElapsedFrameTime;
TimeSlept = sleepAndUpdateCurrent(Math.Max(0, excessFrameTime + accumulatedSleepError));
accumulatedSleepError += excessFrameTime - TimeSlept;
accumulatedSleepError = Math.Max(-1000 / 30.0, accumulatedSleepError);   // 不许攒太多追赶帧
```
Windows 走 `WindowsNativeSleep`，退化才 `Thread.Sleep`（`:40-44,85-86`）。**只有 `Clock.Throttling` 的线程才 sleep；绘制线程在 VSync 下 `MaximumDrawHz=int.MaxValue` → 不 sleep。**

2) **`FrameSync` 档位**（`GameHost.cs:1345-1393`）：`VSync` / `VSyncVRR` / `Limit2x` / `Limit4x` / `Limit8x` / `Unlimited`。
`VSyncVRR` 把 draw 限到 `min(refresh*0.985, max(refresh-2,0))` 且**故意不**等 `WaitUntilNextFrameReady`（VRR 下自己控节奏）。

3) **交换链等待**（A.3）——"一帧只 present 一次"的硬约束所在。

### A.4 一帧的内部顺序
```
（更新线程）Root.UpdateSubTree() → Root.GenerateDrawNodeSubtree() → 写 TripleBuffer<DrawNode>
（绘制线程）WaitUntilNextFrameReady() → TripleBuffer.GetForRead()
         → BeginFrame → 前向不透明 pass（DrawOtherOpaqueInterior，带深度）
         → 后向 pass（DrawOther，深度只测不写）→ FinishFrame → Swap
```
**场景图只在更新线程改，绘制线程拿到只读的 `DrawNode` 树**（三缓冲，读写互不阻塞）——这是"绘制线程不会被 GC/布局卡住"的来源。

### A.5 对我们的判据

- 绘制循环里**禁止** sleep/自旋/`DwmFlush` 对齐；相位只能来自 `FrameLatencyWaitableObject` + `Present(1,0)`（我们已用）。
- 若 `PaceMode=0` 仍 5% 多留一帧，则根因更可能是**等完之后到 Present 之间还有别的阻塞**。lazer 的顺序是"先等，再取早已备好的树"；我们若要等价，就得把等待前移到绘制之前（"等→取缓存图块→present"），而不是"绘制→等→present"。

### C.2 可直接落地的公式

画布高 `H = 768`（mania 逻辑分辨率 `1024×768`，`ManiaPlayfieldAdjustmentContainer` 的 `TargetDrawSize`），命中线距底 `hitPos`：
```
L = H - hitPos                                   // 滚动区高度 = 判定线以上
T = (11485 / scrollSpeed) * (L / (768 - 124.8))
判定线 y = H - hitPos
音符 y   = 判定线 y − (t − now) / T * L          // 向上为负；t=now 时正好压线
长条高   = (end − start) / T * L
```
数值（240Hz）：`scrollSpeed=8` → `T = 1435.6ms`；legacy 默认 `hitPos=124.8` → `L=643.2`，`≈0.448 px/ms ≈ 1.87px/帧`。
`hitPos` 两个来源：skin 的 `HitPosition`，取不到用 `Stage.HIT_TARGET_POSITION = 110`（`Stage.cs:38`）。

### D.3 一个 4K 场景大概几次 draw call（推断，非源码）

音符=1 sprite=1 quad；长条=头+尾+body(同纹理重复采样)；同一列的物件在压平序列里连续 ⇒ 同列合并；跨列纹理不同（`mania-note1/2`）⇒ 切一次。粗估 4K、屏上 30–50 物件 ≈ **10–40 次 draw call**（按 flush 点与布局顺序推断，**未实测**）。

### D.4 映射到 D2D/D3D11

| lazer | 我们的等价物 | 建议 |
|---|---|---|
| 不可变 DrawNode 树 + 三缓冲 | `List<Quad>`（顶点+uv+颜色+纹理槽）每帧重建 + 双/三缓冲交换 | 做，"绘制线程永不阻塞"的根 |
| 状态不变就塞同一个 VB | `D3D11_USAGE_DYNAMIC` + `Map(WRITE_DISCARD)` + 预建索引 + `DrawIndexed` | 做，收益在尾部 |
| body 用 `WrapMode.Repeat` 平铺 | `ID2D1BitmapBrush` 的 `ExtendModeX/Y = Wrap`，或 D3D11 `AddressU/V = Wrap` | 做；长条**不是九宫格**，皮肤作者就是按"一张图铺满整条"设计 |
| 每矩形一次 `FillRectangle`（现状） | 每次都可能切 brush/transform | 按画刷排序，或整体走 D3D11 |

坑：`FillRectangle` 只能 axis-aligned（mania 矩形够用，但光效/爆炸要 `DrawBitmap` 或位图画刷）；**D2D 与自定义 VB 混用只会让状态切换更多，二选一**。

命名：`mania-note{1|2|S}[H|T|L]`、`mania-key{1|2|S}[D]`、`mania-stage-{left|right|bottom|hint|light}`、`mania-hit{300g|300|200|100|50|0}`、`lightingN/L`。

单帧 = `Sprite`，多帧 = `TextureAnimation`（`:36-55`）。

### E.5 新皮肤（argon / triangles）
`ArgonNotePiece`/`DefaultNotePiece` 是**程序化绘制**：矩形 + 圆角 + `EdgeEffect` 发光 + 加色混合，颜色来自 `Column.AccentColour`（= `Colour{col+1}`）；body 的"挖空"用 `BufferedContainer` + `ReverseSubtract`（`DefaultBodyPiece.cs:88-118`）。⇒ **不可复用**（依赖离屏缓冲/混合方程），且它本来不读皮肤文件。我们退化成"纯色矩形 + 每列颜色"即可——正好是现状。

### E.6 皮肤数据在磁盘上的真实形态与可读取性
**问 1：lazer 导入的皮肤存在哪、什么形式？**
答：**realm 的 `SkinInfo` + `RealmNamedFileUsage`，指向内容寻址的 `files/` blob**。不是目录，也不是"字节塞进 realm"。

- `SkinInfo`（`[MapTo("Skin")] : RealmObject`）：`ID`(PK Guid)、`Name`、`Creator`、`InstantiationInfo`、`Hash`、`Protected`、`IList<RealmNamedFileUsage> Files`、`DeletePending` — `osu.Game/Skinning/SkinInfo.cs:13-70`。
- `RealmNamedFileUsage : EmbeddedObject`：只有 `RealmFile File` + `string Filename` — `osu.Game/Models/RealmNamedFileUsage.cs:14-17`。
- `RealmFile`（`[MapTo("File")]`）：只有 `[PrimaryKey] string Hash` — `osu.Game/Models/RealmFile.cs:10-17`。
- 落盘：`RealmFileStore` 用 `storage.GetStorageForDirectory("files")`，按 `data.ComputeSHA2Hash()` 去重 — `osu.Game/Database/RealmFileStore.cs:30-33,48-73`；真实路径由扩展方法 `file.GetStoragePath()` 给出（**该扩展实现未获取到**，与你现场看到的 `files\0\00\<sha256>` 两级分片一致）。
- `skin.ini` 也只是 `Files` 的一个条目，`LegacySkin` 构造时解析 — `osu.Game/Skinning/LegacySkin.cs:75-84`。
- `SkinManager` **没有**扫描 `Skins/` 的分支：`:97` 只挂 `files`，`:99` 构造 `SkinImporter`，`:104-116` 只有内置默认皮肤 ⇒ **你看到 `Skins` 空目录是正常的**。

**问 2：独立进程能不能只读打开 `client.realm`？**
答：**技术上可能，工程上不建议。**
- 文件名由调用方给，自动补 `.realm`；只有 DEBUG 才加 `_<schema>` 后缀 — `RealmAccess.cs:206-219,233-269` ⇒ release 就是 `client.realm`。
- **schema 必须完全对上**：`private const int schema_version = 52;`（`RealmAccess.cs:106`），`new RealmConfiguration(path){ SchemaVersion = schema_version, MigrationCallback = onMigration, FallbackPipePath = ... }`（`:813-827`）。schema 不匹配要么迁移（写库）要么抛；`IsReadOnly` 下无法迁移。⇒ 必须**原样复刻 52 版的全部 `RealmObject`**（realm 要求整 schema 一致，不是三张表就够），等于复刻 `osu.Game` 几百个类，且每次 lazer 升 schema 都要跟。
- 多进程：`FallbackPipePath`（临时目录 `lazer`）说明 Windows 上靠命名管道协调；osu! 运行时会持有 `client.realm.lock`。只读打开并不安全——迁移/锁竞争下会异常或阻塞，而不是优雅降级。⇒ **必须假设"游戏运行时读不了"，失败要能无声降级。**

**问 3：不读 realm 的替代路径？**

| 路径 | 可行性 | 依据 |
|---|---|---|
| lazer 扫描 `Skins/` 目录 | ❌ 不支持 | `SkinManager` 无此分支（问 1） |
| 用户手动 Export 的 `.osk` | ✅ **推荐** | `.osk`=zip；导入侧 `HandledExtensions => new[] { ".osk" }`、`ShouldDeleteArchive` 按扩展名（`SkinImporter.cs:39-43`），导出侧 `RealmArchiveModelExporter`。格式稳定、可离线、只需导一次 |
| stable 明文目录 `%LOCALAPPDATA%\osu!\Skins\<name>\` | ✅ 最佳 fallback | `osu.Game/IO/StableStorage.cs` 专门指向 stable 安装（用 `osu!{user}.cfg` 定位）；stable 皮肤就是明文目录 + `skin.ini` |

**问 4：只能读 realm 的风险与降级**

| 风险 | 后果 | 降级 |
|---|---|---|
| schema 漂移（52→53+） | 打开失败/误迁移 | 版本不匹配直接放弃，绝不迁移 |
| 游戏运行中（锁/管道竞争） | 阻塞或抛异常 | 先探测 `client.realm.lock`，存在即跳过；打开设超时 |
| `IsReadOnly` + schema 不符 | 异常 | 捕获后走 fallback |
| 体积/许可（引入 Realm + 复刻模型） | — | 不做，除非上面全断 |

**建议读取链（P0 就按这个）**：`用户指定目录（含 skin.ini）` → `%LOCALAPPDATA%\osu!\Skins\*` → `用户导出的 .osk` → 内置默认矩形。**永不落到"读 realm"。**

## F. 落地计划
**P0（1–2 天，帧循环改成 lazer 的形状）**
读什么：无（不碰皮肤）。改什么：①删掉绘制循环里的 `Sleep`/`DwmFlush`/自旋，唯一等待是 `FrameLatencyWaitableObject`；②等待点前移到"取当前图块描述"之前，等完到 `Present(1,0)` 之间只做 `BeginDraw/Draw/EndDraw`；③生产路径禁止 `Flush/Map/Query`（截图加显式开关）；④加"每帧只 present 一次"断言与 `Jitter` 统计（口径照 `FramedClock.cs:84-98`）。新增结构：`FrameStats{presentTs, msInPresent, msUntilDisplayed}`（仅验证用）。风险：若根因是 DComp 视觉树合成路径而非相位，改顺序无效 → 转 P1 自绘 + 单 swapchain。验收：PresentMon 2 分钟采样，`Dropped`/`msUntilDisplayed` 尾部改善。

**P1（2–4 天，一帧一个顶点缓冲）**
把"每矩形一次 `FillRectangle`"改成 `List<Quad>` + 一次 `Map(WRITE_DISCARD)` + `DrawIndexed`；body 用 `AddressV=Wrap`；D2D 只留文字/矢量。新增：`Quad{pos,uv,color,texSlot}`、`TextureAtlas`（mania 贴图都很小，一张 2048² 够）。风险：D2D 位图画刷与自定义 VB 混用会让状态切换变多 ⇒ 二选一。验收：RenderDoc 单帧 draw call 降到个位数，PresentMon 尾部不变差。

**P2（皮肤，legacy 优先，argon 退回纯色）**
读什么：`skin.ini`（E.3 全部键）+ 贴图目录/`.osk`（E.6 读取链）。画什么（按依赖序）：列背景+分隔线 → 判定线 → 按键区 → 单点 → 长条（Stretch/Repeat）→ 按键光效。新增：`ManiaSkinConfig`（E.3 字段 + 每列数组）、`SkinTextureSet`（`FallbackColumnIndex` → 贴图名 → 位图）、`SkinResolver`（目录→.osk→默认）。风险：`HitPosition` 会改 `timeRange`（C.1 的 `scale`），**`PreviewClock` 必须跟着改**，否则速度与游戏不一致；`NoteBodyStyle` 2/3/4 在 lazer 里本身就是猜的，我们按 `Repeat` 实现即可，别追求像素级一致。
