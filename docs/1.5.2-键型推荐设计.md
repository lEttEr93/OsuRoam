记录于 2026-11-02，1.5.0 发布之后。对应开发计划里 1.5.2 的第 2 条
（「更方便的键型推荐」）。这份笔记只记**为什么这么设计**和**踩过的坑**，
具体实现等 1.5.2 开工时再落到代码。

## 现状：为什么「推荐偏流」这件事一直说不清

1. `RecommendationEngine` 里键型只值 `patternFit * PatternWeight`，权重 0.12；
   星级 0.73（BPM 的 0.15 已取消，见第 9 节）、探索随机项 0→0.2475。
2. `patternFit` 有两道闸（`RecommendationEngine.cs:92`）：
   - `patternLookup` 要能拿到键型：只有「下载分析过的」或「tag 推断的」两种来源；
   - `patternPreference` 不能是 null：由用户打过的成绩平均而来，**样本 < 3 直接返回 null**。
3. 实测（用户机器）：键型库 5 条真实解析、成绩 214 首 → `patternPreference` 仍是 null，
   于是 `patternFit` 恒为 0。日志里没有 `键型偏好向量：...` 那一行就是没启用。

结论：**「推荐都是 stream」不是引擎偏流**，而是谱池本身如此。

## 实测数据（2026-11-02，4.0–5.0★ 4K，n=216，真值来自 osu.ppy.sh/osu/{id}）

| BPM 桶 | n | Stream | Chordstream | Jacks | 流系主型 |
|---|---|---|---|---|---|
| <120 | 13 | 32% | 18% | 30% | 54% |
| 120–150 | 54 | 32% | 16% | 21% | 48% |
| 150–180 | 60 | 22% | 22% | 9% | 38% |
| 180–220 | 60 | 16% | 29% | 17% | 43% |
| ≥220 | 29 | 30% | 25% | 18% | 55% |

- 流系（Stream + Chordstream，风格上都是 stream）在任何 BPM 段都是最大的一块：38–55%。
- 低 BPM 抬高的是叠键（21–30% vs 中段 9%），不是压低流系。
- 相关很弱：BPM vs Stream −0.06、vs Chordstream +0.13、vs Jacks −0.09。
- 注意 Chordstream / Jumpstream / Handstream 在**风格**上就是 stream，分类器只是按
  「技巧」把它们拆开（单键连打 vs 带和弦的连打）。讨论口径要统一，否则会得出
  「不是流是 4 押流」这种自欺欺人的结论。

工具：`OsuRoam.exe --experiment`（画像对比）、`--experiment=bpm`（BPM 分桶），
真值缓存在 `data/pattern-truth.json`。

## 1.5.2 的设计决定

### 1. 用户显式选键型，取代「从成绩反推」

计划里写的「用户可以自行选择想要游玩的键型（可多选）」正好绕开了上面那道
`patternPreference` 的样本门槛：勾选结果本身就是目标向量，不再依赖 ≥3 个样本。

### 2. 权重语义必须变

现在 `patternFit` 只是 +0.12 的加分项，压在星级（0.62）和随机项（0–0.2475）之下。
但「用户亲手勾了 jumpstream + LN」是**强意图**，按加分项处理等于没听见。
1.5.2 里应该做成硬过滤（至少命中一个勾选项），或把权重抬到能和星级掰手腕。

### 3. LN 是独立维度，不是第 7 个核心型

6 维核心型是 `Stream / Chordstream / Jacks / Coordination / Density / Wildcard`；
LN 是另一条轴：`LnRatio` + 模式标签（RC / LN / Mix / HB），具体子型是
`Release` / `Shield` / `LN Density` 那类。
「勾选 LN」应该实现成 `LnRatio ≥ 阈值` 的过滤，塞进 6 维向量会稀释余弦相似度。

### 4. 预取的是 `.osu`，不是 `.osz`

- `.osu` = 单难度纯文本，20–200 KB，含 `[TimingPoints]` + `[HitObjects]`，
  正好够算键型、CS/OD/AR/HP、BPM、物件数。
- `.osz` = 整个谱面集 zip，2–20 MB，99% 是音频和贴图。
- 接口：`https://osu.ppy.sh/osu/{beatmapId}`，免登录，实测 ~0.5 s / 张。
- 全量 400 张 ≈ 40 MB / 5 分钟；只取 metadata 排序后的前 60 张 ≈ 30 s。
- 必须做 beatmapId 级缓存（`data/pattern-truth.json` 已经有雏形）。
- 注意克制：匿名端点，并发 4 路以内，遇 429 退避。

### 5. 目标是「候选池填满」，不是「抓够 N 个」

**抓取数量本身不是指标。** 如果 400 个候选里只有少数符合用户勾选的键型，
应该**继续往后抓更多 `.osu`**，而不是把分数低的硬塞进推荐池。

推论：
- 预取要有「按命中率决定继续与否」的循环，而不是固定抓 N 张就停；
- 候选来源不够时，要能扩大搜索（换排序、放宽星级、翻页）而不是降低标准。

### 6. 未露面的候选是下一轮的缓冲

没被分析过的候选可以先按元数据排队。下次启动时如果 `.osu` 还没拉够，
这些「尚未露面」的候选正好填补空缺——所以**不要一次性把候选池挥霍光**，
保留一部分作为冷启动的缓冲。

### 7. tag 池要拆成两类

现在曲风 tag（artcore / dnb / phonk…）和键型 tag（stream / jack / chordjack…）
混在同一个列表里，命中比例被平均掉（用户 22 个 tag，命中 1 个只有 5%）。
1.5.2 起：曲风 tag 继续做偏好加分；键型 tag 废弃，交给真值。
注意别误伤曲风那一半。

## 8. tag 池：已改成审核白名单（2026-11-03 落地）

1.5.2 第 1 条（「定期审核的 tag 池」）的数据部分已经做完，机制是：

- 白名单在 `Resources/tag-pool.json`，由 `Tools/build-tag-pool.py` 生成，
  分 6 组：曲风 / 曲目属性 / 语言 / 来源·活动 / 键数 / 键型。组内按审计时的真实出现次数排序。
- **爬到的 tag 不再无条件进池子**：白名单以外的进 `AppSettings.SeenTags`（上限 2000，
  旧的先丢），界面里排在白名单后面，仍然可选、可搜索。
- 别名表只收同一样东西的不同写法（`dnb → drum and bass`、`j-pop → jpop`、`jacks → jack`、
  `ost → original soundtrack`）。子流派各自独立（`heavy metal` 不会并进 `metal`），
  否则用户想精确筛就筛不了。
- `IsMeaningfulTag` 补了排版垃圾的规则：引号 / 括号 / 井号 / 路径 / 运算符一律拒绝，
  `-` `.` `_` 开头的、纯数字的、没有字母的也拒绝。

实测效果（审计者本机 4294 个 `.osu`，6608 个不同 tag）：

| | 之前 | 之后 |
|---|---|---|
| 池子条目 | 16151（几乎全是歌名、艺名、符号） | 152 白名单 + 最多 2000 SeenTags |
| 排序 | 字母序，白名单被淹没 | 白名单按组、按热度在前 |

重跑方式：`python Tools/build-tag-pool.py <tag-counts.json>`，报告会列出「当前库里没出现过」
的条目，用来判断是真冷门还是拼错。

**远程更新**：池子只有一份，放在 `data/tag-pool.json`。每次审核完把这一份传到公开仓库的同名路径，
app 启动时后台拉 `https://raw.githubusercontent.com/lEttEr93/OsuRoam/main/data/tag-pool.json`
（匿名可读，实测 200），内容变了才写本地缓存并刷新界面。

三层来源，优先级从高到低：

| 层 | 位置 | 作用 |
|---|---|---|
| 本地缓存 | `data/tag-pool.json`（程序目录） | 上次远程更新下来的，重启后优先用 |
| 内置 | 程序资源 `OsuRoam.Resources.tag-pool.json` | 拿不到网络时的兜底 |
| 远程 | 公开仓库 `main/data/tag-pool.json` | 启动时拉一次，10 秒超时，失败静默 |

校验：解析失败、分组为空、tag 全空都当无效，继续用旧的那份 —— 不能因为一次坏数据把池子清空。

### 8.1 待审队列与审核流水线（客户端侧已完成）

```
候选谱面 tag
  → 正则/字符粗筛（IsMeaningfulTag：长度、字符集、必须有字母、去掉引号括号井号路径运算符）
  → 白名单/别名命中？命中就结束
  → 没命中 → data/pending-tags.json（上限 500，记次数与首次/末次时间，只存 tag 文本）
  → 用户决定何时提交 → 仓库待审核区
```

**提交通道：内嵌细粒度 PAT（自动提交）**

客户端攒够 30 条、且距上次提交 ≥7 天后，自动往公开仓库开一个 `tag-pool` issue（单次最多 200 条）。
格式是一段 ```` ```json ```` 代码块，`Tools/review-pending-tags.py --issues` 直接能读。

- 凭据：`data/tag-submit-token.txt`（在 `.gitignore` 里，不进仓库），编译时作为资源嵌入。
  没有这个文件 = 自动提交关闭，其它功能不受影响。**要换成 fine-grained PAT（只给 OsuRoam 的 issues:write）**，
  不要用 push 用的那种全权限 token。
- 设置面板有开关「提交待审 tag（只发 tag 与次数）」。
- 提交内容只有 tag 文本与出现次数，不带谱面 ID、歌名、时间线。
- 标签不存在时 GitHub 返回 422，客户端会去掉标签重试一次；其它失败只写日志，不打扰用户。

**待审队列**：`data/pending-tags.json`，上限 500 条，满了先丢「见得最少、最久没见」的。

审核端（`Tools/review-pending-tags.py`）：

```
pending-tags.json 或 issue（label=tag-pool）
  → 去掉已在白名单/别名里的
  → 复数/连字符粗归一 + 相似度聚簇（beginning / beginnings 并成一簇）
  → docs/tag-review/{candidates.json, review.md, prompt.md}
  → AI 只做「归类建议」，且提示词要求拒绝优先、判断不了就 reject
  → 人工确认后改 Tools/build-tag-pool.py 的 TABLE，重跑生成 data/tag-pool.json
```

**实测记录（2026-11-03）**：用全权限 token 对公开仓库真跑了一次提交 —— issue 创建成功、`tag-pool` 标签自动挂上、
`review-pending-tags.py --issues` 能解析出载荷。正文里曾经出现过字面量 `\n`（raw string 里写了 `\n`），
已修并加测试锁死（`testTagSubmitBodyFormat`）。测试 issue 已关闭。

## 9. BPM 不再参与排序（2026-11-03）

原来排序里有 `bpmFit = proximity(beatmap.Bpm, profile.PreferredBpm, 75)`，权重 0.15。
`PreferredBpm` 是**已打谱面 BPM 的中位数**（默认 180）——既不是用户填的，也不代表喜好：

- 一张谱只有一个 `bpm` 字段（第一个非继承时间点），变速谱、BPM 天花板谱全被压成一个数；
- 实测（n=216）BPM 和键型分布几乎无关：vs Stream −0.06、vs Chordstream +0.13、vs Jacks −0.09；
- 低 BPM 段真正变化的是叠键（21–30% vs 中段 9%），不是"慢歌更好听"。

所以整项删掉：`bpmFit` 与它对应的 `ReasonKind.Rhythm` 分支都不再产生，
0.15 权重按比例分给其余三项（0.62/0.10/0.13 → 0.73/0.12/0.15）。
`PlayerProfile.PreferredBpm` 保留，但只用于诊断报告；`ReasonKind.Rhythm` 枚举值保留，
免得旧历史记录按数字反序列化时错位。

回归测试：`testBpmDoesNotAffectRanking`（两张只有 BPM 不同的谱必须同分）。

## 10. 键型推荐 v1（2026-11-03 落地）

设置面板「键型偏好」六个勾选框 = 六个核心型（Stream / Chordstream / Jacks / Coordination / Density / Wildcard），
外加一个「只要面谱（长条 ≥ 25%）」。按之前定的三条口径实现：

| 决定 | 落地方式 |
|---|---|
| 词表 | 只暴露 6 个核心型，勾选结果直接当目标向量 |
| 强度 | **强权重，不硬筛**：`patternFit = 勾选核心型的份额 / 全部核心型份额`，权重 **0.60**（星级折算是 0.73 × 熟悉度权重 ≈ 0.55，两者能掰手腕） |
| LN | 单独一个复选框，`LnRatio ≥ 0.25`（`ManiaPattern.LnChartThreshold`）才算面谱 |

未勾选任何键型时，退回原来「从成绩反推偏好」的路径（`patternPreference`），行为不变。

**已知限制**：`.osu` 预取 v1 已落地（`Services/PatternPrefetcher.cs`），但**只在勾了键型或勾了「只要面谱」时才跑**，
没勾的时候仍然只用「下载分析过的 / tag 推断的」数据。

预取规则（按第 5、6 条）：

- 候选里「还没有真实键型」的谱面，按**离目标星级的距离**排序（抓之前唯一可靠的强信号）；
- 一轮最多 20 张（实测单张 2 秒左右，4 路并发约 10 秒），**命中够了（`max(4, PoolSize×2)`）提前停**；
- 抓过的进 `patterns.json`（`IsInferred: false`），下一轮直接跳过；404/429 的 id 本会话不再重试；
- 剩下的候选留给下一轮 —— 不一次性烧光。

实测 `https://osu.ppy.sh/osu/{id}`：匿名可访问，87 KB / 39 KB 两张分别 2.4 s / 1.9 s（不是设计笔记里写的 0.5 s，
预算按 2 s 估）。

## 11. 按 tag 搜候选（2026-11-03 落地）

osu! 的 `q=` 是**全文匹配**，官方 [Beatmap search](https://osu.ppy.sh/wiki/en/Beatmap_search) 写明它会匹配
artist / title / 难度名 / source / **mapper tags** / user tags。所以「勾了 Jacks 就带 jack 去搜」是可行的。

实测（用客户端凭据直接打 `/api/v2/beatmapsets/search`，`stars>=4 stars<=5 keys=4`）：

| 关键字 | 返回 | 结果标签里含该词 |
|---|---|---|
| 无 | 50 | — |
| `jack` | 50 | **49** |
| `chordjack` | 50 | **50** |
| `stream` | 50 | **48** |
| `ln` | 50 | **50** |
| `tech` | 50 | 31 |

**没有**「按 mapper tag 精确过滤」的参数：网站端的 `tag=` 只匹配 **user tags**（`meta/custom skin` 那种），
lazer 的 `ln=` 过滤器 API 不支持。

落地方式（`Services/PatternSearchHints.cs` + `OsuApiClient`）：

- 勾了键型/面谱 → 先按关键字搜 1–2 页（`sort=relevance`），再跑原来的默认轮换；
  关键字映射：Stream→`stream`、Chordstream→`chordstream`、Jacks→`jack`、Coordination/Density→`ln`、
  Wildcard→`tech`、只要面谱→`ln`。去重后最多两个（多个词是 AND，越多结果越少）。
- 预取队列**先抓 tag 命中的候选**，再按星级距离 —— 命中率远高于盲抽。

**它不是替代，是冷启动加速**：一次搜索 400 条候选里，标签真正点了键型的只有 20（jack）/ 28（ln）/
37（stream+jack）—— tag 覆盖率有限，所以默认轮换那一轮不能去掉。

## 12. 按外部审查意见修管线（2026-11-04）

审查报告：`artifacts/osu-roam/2026-11-04-recommendation-review/out/review.md`。
它的核心结论是：「勾了 Jacks 推不出 jack」不是权重问题，是**管线**问题。按它的第一步已实施：

| 改动 | 之前 | 现在 |
|---|---|---|
| 分析器版本 | 缓存永不过期 | `ManiaPattern.AnalyzerVersion` + `PatternLibrary.TryGetVerified()`；旧版本与 tag 推断都算不可信，预取会重抓 |
| 候选资格 | 预取只看 mode/keys/重复 id | `CandidateFilter.Eligible()`：星级、时长、年份、状态、标签、已装排除 —— 与排名共用同一份条件 |
| 预取排序 | tag 命中优先 → 星级偏远的谱占住预算 | 「乐观分」= 基础分（星级 0.73 + 时长 0.12）+ 0.70×min(1, μ+0.2)；星级跨度大于 tag 加成，所以靠近中心的谱先验证 |
| 探索配额 | 无 | 每 4 个名额留 1 个给「基础分最高但没命中 tag」的候选 |
| 预算 | 20 张/轮，只看命中数 | **16 次 HTTP 尝试**、10 秒截止、4 路并发；提前停 = 已找到 N 张（N=池大小） |
| 线程安全 | `Dictionary` / `HashSet` 并发读写 | 缓存加锁；保存写临时文件后原子替换；fetcher 用 `ConcurrentDictionary` + `Interlocked` |
| 429 / 取消 | 一律记失败 | 429 冷却 60 秒；用户取消不记失败（向上抛） |
| 进度文案 | 「预取 x/y」混了两种进度 | 「已解析 x 张 / 已找到 y 张」 |

## 13. 流式发布 + Verified 资格分流（2026-11-04 落地）

审查的第二步。之前的问题是**顺序**：搜索回调里 `await` 预取，然后才排一次序。所以池子
要么等十几秒才出现，要么在验证没做完时就把 tag 推断的谱面当成「符合键型」展示。

现在拆成两件事：

| | 之前 | 现在 |
|---|---|---|
| 发布时机 | 等预取跑完，一次性排名 | 先发一版临时池，验证每落一批就重排一次（400 ms 节流） |
| 键型来源 | 真实数据优先，缺了就 tag 推断 | 勾选键型 / 只要面谱时**只用真实解析**（`Resolve(..., verifiedOnly: true)`）；没验证到的当「未知」，不拿猜测当结论 |
| 替换规则 | 只追加，不替换 | `PoolReconciler`：正在玩 / 下载 / 导入 / 已预约下一首的卡片锁在最前，其余按新排序原地 `Move`/`Insert`/`RemoveAt`（不 Clear，避免闪烁和滚动归位） |
| 排序随机源 | `Random.Shared`，每次重排都变 | 本轮固定种子（`recommendationSeed`），重排可复现 —— 否则探索项抖动会让卡片一直洗牌 |
| 历史降权 | 池内谱面算「已推荐」，重排会被换掉 | 池内谱面先从 `RecommendationHistory` 里摘出来参与排序，只有真正出池的才降权 |
| 首曲预下载 | 第一版池子的第一张，可能马上被换掉 | 先等验证最多 2.5 秒再挑，挑到的卡片因为已在下载而被锁定，不会被重排冲掉 |
| 代次 | 无 | `poolGeneration`：重建池子（重新开始漫游）后，上一轮的验证任务自动失效 |

锁定的代价：正在下载的那张卡片会一直在池子最前面，即使验证后发现它不那么匹配。
这是有意的 —— 用户已经在下载/玩了，把它从列表里抽走只会更困惑。

**还没做**：统一评分权重表（审查给的 0.700/0.180/… 是待评估起点，没有直接采用）、
离线评估（`evaluate.mjs` 需要先冻结候选快照）。

## 14. 「勾了叠键还是没有叠键」：两个真原因（2026-11-04）

用户的反馈是「勾了 jack，推出来的谱跟 jack 没关系」。查下来不是权重不够，是两件事：

### 14.1 预取在候选集为空时启动，然后把自己标记成「已验证」（真 bug）

用户 11-04 19:10 的日志：

```
19:10:55  读取 mania 4K 成绩样本…
19:10:55  键型预取：候选 0，尝试 0，取回 0，解析 0，命中 0（2 ms）
19:10:55  键型关键字搜索「jack」：50 个谱面集
```

`重建漫游` / 迷你播放器的「下一首」在候选集还没回来（或 `isBusy` 早退）时会调一次
`refillPoolAsync()`，于是验证以「候选 0」跑完一轮；而流式发布用
`verificationGeneration == poolGeneration` 判断「这一代验证过了」，
**于是整个漫游再没验证过一张谱**。而新排序只认已验证的键型 →
`patternFit` 恒为 0 → 排序退化成纯基础分 → 看起来「跟勾的键型无关」。

修法：
- 候选为空时**不起**验证（也不占代次名额）；
- 同一代里候选数量翻倍才补跑一轮（分批到达时不至于每批都烧预算）；
- `publishPoolAsync` 在候选为空时直接返回，避免空排序把池子清掉。

### 14.2 探索度噪声比键型信号还大

默认 `Exploration = 0.45`，随机项 `0.45 × 0.55 ≈ 0.25`；
而「叠键占比 25%」只能拿到 `0.60 × 0.25 = 0.15`。**噪声盖过信号**。
勾了键型时把探索项压到 0.35 倍。

### 14.3 实测（用用户真实配置跑离线探针）

`Tests` 加了 `--probe` 模式：用本机 `settings.json` 的凭据拉真实候选、抓 `.osu` 解析，
落一份快照 CSV（`D:\AI\scratch\probe-1104-fixed\snapshot.csv`），可复用做回归。

用户配置（4.1–4.9★ / 4K / 19 个 tag / 严格 ranked+loved / 排除已玩）：
400 个候选谱面集 → 46 个合格难度 → 抓 40 张解析。

| 排序 | 叠键 ≥ 25% 的 top5 | 叠键 ≥ 50% 的 top5 |
|---|---|---|
| 没有键型数据（基线） | 3/5 | 1/5 |
| 修复后（0.60 × share，探索 ×0.35） | **5/5** | 2/5 |

也就是说：**只要真验证过，结果就是叠键谱**。用户看到「没关系」是因为 14.1 让验证根本没跑。

### 14.4 卡片上直接写占比

勾了键型时，推荐理由追加「叠键 79%」这样的标签（`ReasonCategory`）。以前卡片只显示
分析器的分类名（Jumpstream Tech 之类），用户无法判断这张谱到底符不符合自己的勾选，
只能凭感觉 —— 这是「感知不到」的第三层原因。

## 15. 候选不够就继续翻页（2026-11-04）

用户的提问很对：「没找到就扩大范围继续找」。查了 API 的边界，问题不在 osu! 那边：

| 项 | 事实 |
|---|---|
| 单页条数 | 50（`/beatmapsets/search`，服务端定死） |
| 分页 | `cursor_string` 游标，换 `sort` 必须重置 |
| 服务端命中数 | 响应里的 `total`。实测 4.1–4.9★ × 4K mania × 45–360s 约 **54,300** 个谱面集 |
| 我们的旧上限 | **8 页 = 400 条/次漫游**（`resultCount < 400` 硬截断） |

也就是说「候选有限」是我们自己截的。实测同一套筛选条件（19 条 tag 白名单、ranked/loved、
排除已玩、「排除已安装谱面」开着、本机 4215 个已装难度）：

| 页数 | 候选谱面集 | 通过筛选的难度 | 排除已安装后仍可推荐 |
|---|---|---|---|
| 8 页（旧） | 400 | 50 | **1** |
| 24 页 | 1,200 | 276 | **210** |

24 页约 10 秒，而且流式发布让池子边到边填、填满就停，常见情况只花 1–2 秒。

改动：
- `SearchCandidatesInBatchesAsync` 增加 `wantsMore` / `maximumPages`：常规 8 页之后，
  只要「池子还没填满」就继续翻（上限 24 页 = 1,200 条）。
- 严格条件（含「排除已安装谱面」）下算出空池时，**临时忽略这一条**重排一次，
  并在状态栏说明「本轮有 N 首是你下过的」——已安装只是「下过」，不是「不喜欢」，
  不该让整轮推荐变成死胡同。
- `--diag pages:N installed` 可以复现上面的表。

## 16. 候选不足时：放宽补位 + 继续翻页 + 找到就替换（2026-11-04）

用户要的行为：**严格条件优先，不够就把 tag 降级成加权、允许玩过的谱面掺一点；同时提示「候选不足」，
后台继续翻页，一旦找到够格的就把凑数的换掉。**

两段式排序：

| 段 | 条件 | 标记 |
|---|---|---|
| 严格 | 白名单 tag **硬筛**；「已推荐/已玩」按排除或者大幅降权处理；排除 tag 永远硬 | 正常卡片 |
| 补位 | 白名单 tag **降级为加权**（tagFit 仍加分）；已推荐/已玩过的允许上来；排除 tag / 状态 / 星级 / 时长仍然硬 | `IsFallback = true`，理由后加「放宽补位」 |

- 池子永远先排严格段；补位只填剩下的名额，所以够格的一出现就自然把它们挤掉
  （`PoolReconciler` 每次重排都会把排序结果对齐到卡片列表，补位卡片随之消失）。
- 状态栏：`符合口味的候选不够：4 首是按放宽条件补的（tag 降级为加权 / 允许已玩过），1 首够格；
  正在继续翻页，够格的一出现就替换`。
- 翻页条件从「池子空」改成「**还有补位卡片**」：`wantsMore: () => 卡片里非补位的数量 < PoolSize`，
  上限 24 页。所以补位只是过渡态，不会让翻页停下来。
- 严格条件一个都不剩时，才进一步放开「排除已安装谱面」（上一节）。

实测（本机配置，排除已安装开着，4215 个已装难度）：

| 页数 | 严格 | 补位 |
|---|---|---|
| 8 页（旧上限） | 1 | 4（Night of Knights / Intersect Thunderbolt-Remix / C18H27NO3 / LegenD.） |
| 24 页（新） | **5** | **0** |

## 17. 关键字搜索翻页 + 按真实键型甄别（2026-11-04）

### 17.1 为什么之前翻页没用

默认排序（`ranked_desc` / `ranked_asc` / `plays_desc` / `favourites_desc` / `difficulty_desc`）
都是**头部强偏置**：`stars 4.1–4.9 keys=4` 服务端命中约 10,000 个谱面集，翻到第 24 页只覆盖 8–12%，
而且是最新/最老/最热的那几段。实测：用户键型库里的四张叠键谱（SCOPIN 4.56★、Lost Umbrella 4.41/4.76★、
Hold On Tight 4.50★、Overkill 4.79★）全部是 ranked、全部在星级窗口内、tag 也全部命中白名单，
**却在 1,200 个候选里一次都没出现**。所以「扩大页数」扩大的是同一分布的深度，不是广度。

### 17.2 关键字查询才是对症的那一档

| 查询 | 深度 | 通过 tag 白名单 | 捞到已知叠键谱 |
|---|---|---|---|
| 默认排序 | 1,200 条 | 198（16%） | 0 |
| `q=jack` | 300 条（6 页） | 每页 17–32（≈48%） | **1（SCOPIN）** |

`q=jack` 服务端约 3,036 条命中，所以每个关键字翻 4 页（`HintPageBudget`），
池子一旦被够格候选填满就立刻停止翻页（`enoughStrictCandidates`）。

### 17.3 不靠 tag，也不靠曲名/作者排除

`q=` 是全文匹配，会连带命中曲名/作者里的 "jack" 之类（人名）。按用户要求**不做关键词排除**，
而是把这类候选标记成「关键字召回」（`keywordBeatmapsetIds`）：

- 预取阶段：tag 白名单不作门槛（`CandidateFilter.Eligible(ignoreTagWhitelist: true)`），
  并且 `Optimistic += 1.0` 排在最前面 —— 它们是「对症」的那一小撮。
- 排序阶段：tag 不符但属于关键字召回的谱面，**只有真实解析出的键型占比 ≥ `KeywordShareFloor`（0.25）**
  （或「只要面谱」时确认为 LN 谱）才进池。曲名碰巧含 jack 的普通谱到此为止。

### 17.4 代价与收敛

关键字候选每次漫游最多验证 16 张（`DefaultBudget`），一轮通常命中 1–2 张；
键型库是持久化的，所以「哪些关键字候选真的是叠键」会跨轮累积，多跑几轮后命中率上升。

## 18. 「下载全卡住」：快照队列改成可重排调度（2026-11-04）

现场症状（用户 21:28 那次冷启动）：池子 9 次重排里 7 次「锁定 0」，2 张谱面分别用 87 秒 / 37 秒才下完，
期间池子里所有卡片都在等，还出现一次 `预下载的谱面文件不存在`。

逐条查下来是五件事叠加：

| # | 缺陷 | 位置 |
|---|---|---|
| 1 | 预下载队列是**开始时拍的快照**，逐个 `await` 跑到底 | 原 `prefetchPoolAsync` |
| 2 | `prefetching` 期间新的 publish **不再下新卡** | 同上 |
| 3 | 下载服务**全局串行**（`SemaphoreSlim(1,1)`），单镜像 12–28 MB 要 37–87 秒 | `BeatmapDownloadService` |
| 4 | 排队中的卡片**不被锁定**（只锁 `Queued/Downloading/Importing`），被换掉后队列白走 | `pinnedBeatmapsetIds` |
| 5 | `Downloading` 被当成「文件已就绪」，跳过下载直接导入 → `FileNotFoundException` | `downloadItemAsync` |

改法：

- **可重排调度**（`schedulePoolDownloads`）：每次池子重排重新算待下清单，
  用 `Dictionary<int, PoolDownload>` 记录在途任务；出池的取消（并删 `.part`），新进池的按优先级插队。
- **优先级**（`PoolDownloadPlanner`）：正在玩 / 已预约 → 够格（非补位）→ 补位垫底；
  失败过一次的不再自动重试，避免失败即重试的死循环。
- **补位让位**：够格候选在等空位、而通道被补位卡片占着时，直接取消那张补位下载。
- **在途下载可等待**：`downloadItemAsync` 遇到同一张卡的在途任务就 `await` 它
  （`ownedByScheduler` 标志防止调度器自己等自己），不再把 `Downloading` 当就绪。
- **并发 2 路**（`BeatmapDownloadService.MaxConcurrentDownloads`），并且只有 `Downloaded` 且文件存在才算就绪。
- **在途即锁定**：`pinned = playing/prepared/current ∪ 在途下载`，中途不会被换掉。


### 18.1 事故：取消判据用错，出现每秒 2800 次的取消循环（1.5.2+6 → +7）

1.5.2+6 上线后，用户 21:45 那次运行 30,263 行日志里有 **30,025 行是「预下载取消」**，峰值 2,853 次/秒，
`让位 0`、`下载完成 13` —— 下载永远跑不完。

原因：判断「要不要取消在途下载」时，我拿的是**待下载清单**
（`DownloadState is Waiting or Failed`）。可这张卡一开始下载，状态就变成 `Queued`/`Downloading`，
于是它从清单里消失 → 被判成「已经不在池子里」→ 取消；取消又把状态打回 `Waiting` → 立刻重启 → 死循环。

修法：判据改成**池内成员资格**（`PoolDownloadPlanner.ShouldCancel`）：
只有「卡片真的离开池子」或「已经下完（Downloaded/Imported/Importing）」才取消。
另外让位过的补位卡记进 `poolDownloadRetried`，不再自动排队，避免「让位 → 重排 → 又让位」的抖动。
顺带补了 `authorizeAsync` 的重试 —— 那次漫游一开始就是因为取 token 的 SSL 抖动直接失败的。
