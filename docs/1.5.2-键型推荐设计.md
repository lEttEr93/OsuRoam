记录于 2026-11-02，1.5.0 发布之后。对应开发计划里 1.5.2 的第 2 条
（「更方便的键型推荐」）。这份笔记只记**为什么这么设计**和**踩过的坑**，
具体实现等 1.5.2 开工时再落到代码。

## 现状：为什么「推荐偏流」这件事一直说不清

1. `RecommendationEngine` 里键型只值 `patternFit * PatternWeight`，权重 0.12；
   星级 0.73（BPM 的 0.15 已取消，见第 9 节）、探索随机项 0→0.2475。
2. `patternFit` 有两道闸（`RecommendationEngine.cs:92`）：
   - `patternLookup` 要能拿到键型：只有「下载分析过的」或「tag 推断的」两种来源；
   - `patternPreference` 不能是 null：由用户打过的成绩平均而来，**样本 < 3 直接返回 null**。
3. 实测（用户机器）：键型库 5 条真实解析、成绩 214 首 → `patternPreference` 仍是 null，
   于是 `patternFit` 恒为 0。日志里没有 `键型偏好向量：...` 那一行就是没启用。

结论：**「推荐都是 stream」不是引擎偏流**，而是谱池本身如此。

## 实测数据（2026-11-02，4.0–5.0★ 4K，n=216，真值来自 osu.ppy.sh/osu/{id}）

| BPM 桶 | n | Stream | Chordstream | Jacks | 流系主型 |
|---|---|---|---|---|---|
| <120 | 13 | 32% | 18% | 30% | 54% |
| 120–150 | 54 | 32% | 16% | 21% | 48% |
| 150–180 | 60 | 22% | 22% | 9% | 38% |
| 180–220 | 60 | 16% | 29% | 17% | 43% |
| ≥220 | 29 | 30% | 25% | 18% | 55% |

- 流系（Stream + Chordstream，风格上都是 stream）在任何 BPM 段都是最大的一块：38–55%。
- 低 BPM 抬高的是叠键（21–30% vs 中段 9%），不是压低流系。
- 相关很弱：BPM vs Stream −0.06、vs Chordstream +0.13、vs Jacks −0.09。
- 注意 Chordstream / Jumpstream / Handstream 在**风格**上就是 stream，分类器只是按
  「技巧」把它们拆开（单键连打 vs 带和弦的连打）。讨论口径要统一，否则会得出
  「不是流是 4 押流」这种自欺欺人的结论。

工具：`OsuRoam.exe --experiment`（画像对比）、`--experiment=bpm`（BPM 分桶），
真值缓存在 `data/pattern-truth.json`。

## 1.5.2 的设计决定

### 1. 用户显式选键型，取代「从成绩反推」

计划里写的「用户可以自行选择想要游玩的键型（可多选）」正好绕开了上面那道
`patternPreference` 的样本门槛：勾选结果本身就是目标向量，不再依赖 ≥3 个样本。

### 2. 权重语义必须变

现在 `patternFit` 只是 +0.12 的加分项，压在星级（0.62）和随机项（0–0.2475）之下。
但「用户亲手勾了 jumpstream + LN」是**强意图**，按加分项处理等于没听见。
1.5.2 里应该做成硬过滤（至少命中一个勾选项），或把权重抬到能和星级掰手腕。

### 3. LN 是独立维度，不是第 7 个核心型

6 维核心型是 `Stream / Chordstream / Jacks / Coordination / Density / Wildcard`；
LN 是另一条轴：`LnRatio` + 模式标签（RC / LN / Mix / HB），具体子型是
`Release` / `Shield` / `LN Density` 那类。
「勾选 LN」应该实现成 `LnRatio ≥ 阈值` 的过滤，塞进 6 维向量会稀释余弦相似度。

### 4. 预取的是 `.osu`，不是 `.osz`

- `.osu` = 单难度纯文本，20–200 KB，含 `[TimingPoints]` + `[HitObjects]`，
  正好够算键型、CS/OD/AR/HP、BPM、物件数。
- `.osz` = 整个谱面集 zip，2–20 MB，99% 是音频和贴图。
- 接口：`https://osu.ppy.sh/osu/{beatmapId}`，免登录，实测 ~0.5 s / 张。
- 全量 400 张 ≈ 40 MB / 5 分钟；只取 metadata 排序后的前 60 张 ≈ 30 s。
- 必须做 beatmapId 级缓存（`data/pattern-truth.json` 已经有雏形）。
- 注意克制：匿名端点，并发 4 路以内，遇 429 退避。

### 5. 目标是「候选池填满」，不是「抓够 N 个」

**抓取数量本身不是指标。** 如果 400 个候选里只有少数符合用户勾选的键型，
应该**继续往后抓更多 `.osu`**，而不是把分数低的硬塞进推荐池。

推论：
- 预取要有「按命中率决定继续与否」的循环，而不是固定抓 N 张就停；
- 候选来源不够时，要能扩大搜索（换排序、放宽星级、翻页）而不是降低标准。

### 6. 未露面的候选是下一轮的缓冲

没被分析过的候选可以先按元数据排队。下次启动时如果 `.osu` 还没拉够，
这些「尚未露面」的候选正好填补空缺——所以**不要一次性把候选池挥霍光**，
保留一部分作为冷启动的缓冲。

### 7. tag 池要拆成两类

现在曲风 tag（artcore / dnb / phonk…）和键型 tag（stream / jack / chordjack…）
混在同一个列表里，命中比例被平均掉（用户 22 个 tag，命中 1 个只有 5%）。
1.5.2 起：曲风 tag 继续做偏好加分；键型 tag 废弃，交给真值。
注意别误伤曲风那一半。

## 8. tag 池：已改成审核白名单（2026-11-03 落地）

1.5.2 第 1 条（「定期审核的 tag 池」）的数据部分已经做完，机制是：

- 白名单在 `Resources/tag-pool.json`，由 `Tools/build-tag-pool.py` 生成，
  分 6 组：曲风 / 曲目属性 / 语言 / 来源·活动 / 键数 / 键型。组内按审计时的真实出现次数排序。
- **爬到的 tag 不再无条件进池子**：白名单以外的进 `AppSettings.SeenTags`（上限 2000，
  旧的先丢），界面里排在白名单后面，仍然可选、可搜索。
- 别名表只收同一样东西的不同写法（`dnb → drum and bass`、`j-pop → jpop`、`jacks → jack`、
  `ost → original soundtrack`）。子流派各自独立（`heavy metal` 不会并进 `metal`），
  否则用户想精确筛就筛不了。
- `IsMeaningfulTag` 补了排版垃圾的规则：引号 / 括号 / 井号 / 路径 / 运算符一律拒绝，
  `-` `.` `_` 开头的、纯数字的、没有字母的也拒绝。

实测效果（审计者本机 4294 个 `.osu`，6608 个不同 tag）：

| | 之前 | 之后 |
|---|---|---|
| 池子条目 | 16151（几乎全是歌名、艺名、符号） | 152 白名单 + 最多 2000 SeenTags |
| 排序 | 字母序，白名单被淹没 | 白名单按组、按热度在前 |

重跑方式：`python Tools/build-tag-pool.py <tag-counts.json>`，报告会列出「当前库里没出现过」
的条目，用来判断是真冷门还是拼错。

**远程更新**：池子只有一份，放在 `data/tag-pool.json`。每次审核完把这一份传到公开仓库的同名路径，
app 启动时后台拉 `https://raw.githubusercontent.com/lEttEr93/OsuRoam/main/data/tag-pool.json`
（匿名可读，实测 200），内容变了才写本地缓存并刷新界面。

三层来源，优先级从高到低：

| 层 | 位置 | 作用 |
|---|---|---|
| 本地缓存 | `data/tag-pool.json`（程序目录） | 上次远程更新下来的，重启后优先用 |
| 内置 | 程序资源 `OsuRoam.Resources.tag-pool.json` | 拿不到网络时的兜底 |
| 远程 | 公开仓库 `main/data/tag-pool.json` | 启动时拉一次，10 秒超时，失败静默 |

校验：解析失败、分组为空、tag 全空都当无效，继续用旧的那份 —— 不能因为一次坏数据把池子清空。

### 8.1 待审队列与审核流水线（客户端侧已完成）

```
候选谱面 tag
  → 正则/字符粗筛（IsMeaningfulTag：长度、字符集、必须有字母、去掉引号括号井号路径运算符）
  → 白名单/别名命中？命中就结束
  → 没命中 → data/pending-tags.json（上限 500，记次数与首次/末次时间，只存 tag 文本）
  → 用户决定何时提交 → 仓库待审核区
```

**提交通道：内嵌细粒度 PAT（自动提交）**

客户端攒够 30 条、且距上次提交 ≥7 天后，自动往公开仓库开一个 `tag-pool` issue（单次最多 200 条）。
格式是一段 ```` ```json ```` 代码块，`Tools/review-pending-tags.py --issues` 直接能读。

- 凭据：`data/tag-submit-token.txt`（在 `.gitignore` 里，不进仓库），编译时作为资源嵌入。
  没有这个文件 = 自动提交关闭，其它功能不受影响。**要换成 fine-grained PAT（只给 OsuRoam 的 issues:write）**，
  不要用 push 用的那种全权限 token。
- 设置面板有开关「提交待审 tag（只发 tag 与次数）」。
- 提交内容只有 tag 文本与出现次数，不带谱面 ID、歌名、时间线。
- 标签不存在时 GitHub 返回 422，客户端会去掉标签重试一次；其它失败只写日志，不打扰用户。

**待审队列**：`data/pending-tags.json`，上限 500 条，满了先丢「见得最少、最久没见」的。

审核端（`Tools/review-pending-tags.py`）：

```
pending-tags.json 或 issue（label=tag-pool）
  → 去掉已在白名单/别名里的
  → 复数/连字符粗归一 + 相似度聚簇（beginning / beginnings 并成一簇）
  → docs/tag-review/{candidates.json, review.md, prompt.md}
  → AI 只做「归类建议」，且提示词要求拒绝优先、判断不了就 reject
  → 人工确认后改 Tools/build-tag-pool.py 的 TABLE，重跑生成 data/tag-pool.json
```

**实测记录（2026-11-03）**：用全权限 token 对公开仓库真跑了一次提交 —— issue 创建成功、`tag-pool` 标签自动挂上、
`review-pending-tags.py --issues` 能解析出载荷。正文里曾经出现过字面量 `\n`（raw string 里写了 `\n`），
已修并加测试锁死（`testTagSubmitBodyFormat`）。测试 issue 已关闭。

## 9. BPM 不再参与排序（2026-11-03）

原来排序里有 `bpmFit = proximity(beatmap.Bpm, profile.PreferredBpm, 75)`，权重 0.15。
`PreferredBpm` 是**已打谱面 BPM 的中位数**（默认 180）——既不是用户填的，也不代表喜好：

- 一张谱只有一个 `bpm` 字段（第一个非继承时间点），变速谱、BPM 天花板谱全被压成一个数；
- 实测（n=216）BPM 和键型分布几乎无关：vs Stream −0.06、vs Chordstream +0.13、vs Jacks −0.09；
- 低 BPM 段真正变化的是叠键（21–30% vs 中段 9%），不是"慢歌更好听"。

所以整项删掉：`bpmFit` 与它对应的 `ReasonKind.Rhythm` 分支都不再产生，
0.15 权重按比例分给其余三项（0.62/0.10/0.13 → 0.73/0.12/0.15）。
`PlayerProfile.PreferredBpm` 保留，但只用于诊断报告；`ReasonKind.Rhythm` 枚举值保留，
免得旧历史记录按数字反序列化时错位。

回归测试：`testBpmDoesNotAffectRanking`（两张只有 BPM 不同的谱必须同分）。
